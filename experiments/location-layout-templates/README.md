и в старых review-файлах отражают состояние до этого обновления.

Экспериментальное исследование и коллекция из **12 выразительных шаблонов локаций** (6 типов мест × 2 контрастных варианта планировки), собранных детерминированным генератором проекта (`DeterministicLayoutProvider`) из контракта `LayoutIntent` и отрисованных текущим игровым рендерером (`LocationMapSvg`, React SSR).

Цель эксперимента — проверить, можно ли заранее создавать качественные, композиционно ясные и пригодные для тактической игры карты, которые позже будут использоваться ИИ-мастером при процедурной генерации кампаний без ручной расстановки каждой клетки.

## 2. Архитектура и конвейер сборки

Конвейер строго соблюдает контракты TaleForge без расширения production-кода:

```text
  [ LayoutIntent ]  (замысел: части, размеры, стороны примыкания, полосы рельефа, детали)
         │
         ▼
[ DeterministicLayoutProvider ]  (укладка коробок, лестниц, открытых стыков, подходов)
         │
         ├──► [ validation.validate ] (проверка лимитов, стыков рельефа, связности)
         │
         ▼
    [ Blueprint ]  (чистые неизменяемые данные комплекса)
         │
         ├──► [ geometry.build_area ] (генерация масок пола, твердых стен, проходов, reachability)
         │
         ▼
[ MapLocationPlan / Sketch ]
         │
         ▼
[ LocationMapSvg (React SSR) ]  (векторный SVG с темами, глифами и стилями)
```

Каждый шаблон хранится в изолированной папке:
```text
experiments/location-layout-templates/templates/<template_id>/
  ├── metadata.json       # Описание концепта, геймплейных зон, адаптаций, ограничений
  ├── intent.json         # Исходный валидный LayoutIntent
  ├── blueprint.json      # Собранный Blueprint
  ├── validation.json     # Результаты тестов seed (1, 7, 42, 99, 123) и отчет по деталям
  ├── render_payload.json # Данные для веб-рендерера
  └── previews/
      ├── overview_level_0.svg   # Общий план основного уровня
      ├── overview_level_-1.svg  # Общий план подземного уровня (если есть)
      └── area_<ref>.svg         # Изолированный план каждого участка
```

## 3. Воспроизведение сборки и рендеринга

1. **Сборка и валидация всех 12 шаблонов (Python)**:
   ```bash
   uv run python experiments/location-layout-templates/scripts/build_templates.py
   ```
   Скрипт проверяет каждый шаблон на 5 seed (`1`, `7`, `42`, `99`, `123`), проверяет валидацию, связность проходов, строит геометрию всех комнат и сохраняет JSON-артефакты.

2. **Рендеринг SVG-превью игровым рендерером (Node / Vite SSR)**:
   ```bash
   cd web
   node scripts/export-experiment-previews.mjs
   ```
   Скрипт компилирует компонент `LocationMapSvg` через Vite SSR и генерирует 55 самодостаточных SVG-файлов в папках `previews/`.

## 4. Ключевые системные ограничения генератора

1. **Ширина дверей и проходов**:
   - Межкомнатные двери (`door`) жестко ограничены 1 клеткой. Широкие проходы (> 1 клетки) допустимы только для `edge`, `arch`, `gate`, `gap`.
   - В `PartIntent.passage_kind` значение `edge` запрещено схемой валидации: провайдер автоматически назначает `edge` только на стыках двух участков `outdoor`.

2. **Автоматический сдвиг деталей при конфликтах (`_place_details`)**:
   - Если деталь попадает в створ дверного проема или выходит за пределы эродированной маски пола (`cave` или `l_shape`), алгоритм детерминированно смещает её на ближайшую свободную клетку. Это предотвращает фатальные ошибки, но требует авторского внимания к границам проемов.

3. **Сквозные полосы рельефа (`BandIntent`)**:
   - Дороги (`road`), тропы (`path`) и ручьи (`stream`) действуют только на `outdoor`.
   - Пересечение `road`/`path` и `stream` автоматически генерирует `bridge`.
   - На стыках открытых участков полосы должны абсолютно точно совпадать по координатам сетки плана, иначе валидатор бракует комплекс (`_joints`).

4. **Многоуровневость**:
   - Участки разных уровней могут соединяться строго вертикальными связями (`stairs` или `hatch`). Провайдер смещает проекцию нижнего участка по оси X (`ox + k * cols`), размещая лестницу на свободной стороне.
