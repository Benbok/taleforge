# Taleforge

Текстовая ролевая игра с ИИ-мастером по правилам D&D 5e (SRD 5.1).

ИИ — голос, приложение — мир: вся механика, числа и состояние живут в коде и данных, модель только описывает и вызывает инструменты.

Техническое задание и документы мира — в [docs/](docs/README.md).

## Структура

```
app/
  rules/          # движок правил: интерфейс RulesEngine, кубики
    dnd5e/        # реализация по SRD 5.1
  content/        # загрузка и проверка пакетов контента, ядровая схема
  core/           # кампании, места, приглашения, чат, сеансы, персонажи, состояние мира
  api/            # REST: вход, кампании, приглашения, персонажи, админка
  gateway/        # WebSocket-шлюз и доставка событий (память или Redis)
  db/             # модели SQLAlchemy; схема меняется миграциями alembic/
  web/dist/       # сборка клиента (не в git)
  tools/          # инструменты мастера: схема + обработчик, журнал событий с обратной дельтой
  agents/         # ИИ-мастер: ход (решение → повествование), промпты, доступ к моделям через LiteLLM
web/              # клиент: React + TypeScript + Vite, Zustand, Tailwind
content/
  dnd5e-srd/      # базовый пакет правил (SRD 5.1, CC BY 4.0)
  echo-leviathans/ # пакет мира «Эхо Левиафанов»: происхождения, классы, Резонанс и его выводки, предметы, локации, лор
tests/
```

Базовый пакет содержит 334 существа, 12 классов и 9 рас SRD; их пересобирает `tools/import_srd.py` из открытого
набора 5e-bits. Пакеты сеттинга лежат рядом с базовым в `content/<id>/` и подключают его через `ruleset_base: srd-5.1`.

## Запуск

Игра на своей машине:

```
cp .env.example .env          # задайте SUPERADMIN_*, JWT_SECRET
docker compose up --build     # http://localhost:8000
docker compose --profile tunnel up --build   # то же + публичная ссылка cloudflared (адрес в логах tunnel)
```

Клиент собирается внутри образа. Для разработки интерфейса:

```
cd web && npm install
npm run dev        # http://localhost:5173, запросы к API и WebSocket уходят на сервер :8000
npm test           # тесты клиента (Vitest)
npm run build      # проверка типов и сборка в app/web/dist, её раздаёт сервер
```

Без сборки сервер отдаёт на `/` прежний клиент. Тема интерфейса (палитра, шрифты, подписи) задаётся в `theme`
пакета сеттинга, см. `app/content/theme.py`: раскладку и виджеты пакет не меняет, нечитаемую тему импорт отклоняет.

## ИИ-мастер

Ключ модели кладётся в `.env` и живёт только на сервере:

```
ANTHROPIC_API_KEY=sk-ant-…                              # мастер Claude (по умолчанию)
GEMINI_API_KEY=…                                         # Gemini
LM_STUDIO_API_BASE=http://host.docker.internal:1234/v1   # локальная модель в LM Studio
```

Модели настраиваются в **Профиле** (Admin и Super Admin, раздел «Модели ИИ»): там видно, задан ли ключ каждого провайдера,
добавляются модели (Claude, Gemini, LM Studio), а кнопка «Проверить» отправляет модели короткий запрос и показывает,
ответила ли она и за сколько. Super Admin отмечает модель по умолчанию для новых кампаний. При создании кампании мастер
выбирается из этих моделей, а владелец может сменить модель мастера в комнате кампании кнопкой «Модель мастера».

Для LM Studio включите в нём сервер (Developer → Start Server), добавьте модель с провайдером «Локальная» и нажмите
«Загрузить модели из LM Studio», чтобы выбрать имя из списка. Адрес сервера можно задать у модели, иначе берётся
`LM_STUDIO_API_BASE`. Локальным моделям нужна поддержка вызова инструментов (tool use).

Как ходит мастер: игроки пишут действия, мастер ждёт реплик от всех героев (или `collect_window_sec`, по умолчанию 60 с),
затем вызывает инструменты (броски, атаки, эффекты, предметы, существа) и описывает итог. Числа считает только сервер;
каждый вызов модели пишется в `llm_calls` с токенами и стоимостью, а `spend_limit_usd` в настройках кампании
останавливает мастера при превышении. Сбой хода откатывает все его изменения.

При создании кампании владелец заполняет анкету: длительность, масштаб угрозы, чего больше (бои, исследование,
интриги, мистика, головоломки), какие эмоции нужны, пожелания и запретные темы. Анкета попадает мастеру в системную
инструкцию. Характер ИИ-мастера задаёт персона: серьёзность, юмор, мрачность, подробность, темп, манера и суровость
подачи. Есть встроенные персоны, свои Admin заводит в профиле. Кампания хранит копию персоны, сменить её можно
в комнате кнопкой «Характер мастера».

До первой сессии архитектор сюжета строит каркас кампании по анкете и лору пакета: завязку, 1–3 антагониста
с планом угрозы, акты с ключевыми точками, наброски локаций и NPC, тайны (у каждой не меньше трёх зацепок)
и 2–3 возможных финала. Опорой служит шаблон сюжета из пакета (`plot_structure`: расследование, ограбление,
путешествие, осада, выживание, интрига, охота на чудовище), подобранный по анкете. Сервер проверяет ссылки
на шаблоны, объём по длительности, зацепки и запретные темы и возвращает ошибки архитектору, до трёх попыток.
Каркас видит только место мастера; владелец и игроки видят афишу (название, фраза, теги) и завязку. До начала
игры можно попросить другой вариант с пожеланием, перед этим показывается примерная стоимость. Версии хранятся
в `campaign_plans`.

В игре мастер ведёт по каркасу. В системную инструкцию попадает не весь каркас, а «Сюжет сейчас»: текущий акт
с узлами и итогами, тайны этого акта с зацепками, места и NPC рядом, следующий шаг каждого злодея. Весь каркас
мастер читает инструментом `get_plot`. Прогресс он отмечает сам: `advance_plot` (узел пройден или обойдён,
с итогом), `plot_reveal` (герои узнали правду), `end_act` (акт закрыт, открыт следующий). Наброски мест и NPC
он разворачивает `develop`, когда отряд до них дошёл: детали записываются в каркас, а место или NPC появляется
в реестре мира. Злодеи действуют сами: мастер двигает план угрозы `threat_tick`, а сервер — раз в 3 игровых
дня в короткой кампании и раз в 5 в длинной (в ваншоте часы не идут). После закрытия акта архитектор в фоне
пересматривает оставшиеся акты с учётом итогов, у ИИ-мастера и если владелец не выключил `settings.replan`.
Пересмотр ложится только на акты, в которых ещё ничего не прошли; каждая версия сохраняется в `campaign_plans`.
События этих инструментов скрыты от игроков, как и итог пересмотра.

Перед игрой мастер задаёт каждому игроку 2–3 вопроса о связях героя с завязкой и отрядом (лист героя, блок
«Связи героя»). Пока у кампании нет каркаса или мастер — человек, вопросы стандартные; ИИ-мастер с каркасом
заменяет их своими, пока на них не ответили. Ответ можно пометить личным: его увидят только игрок и мастер,
открытые ответы видны всем за столом. По ответам ИИ-мастер тайно привязывает героя к узлу, NPC, злодею или месту
каркаса (личный крючок); то же можно сделать при проверке героя (`review_character`, поле `hook_ref`).
Крючки и связи мастер видит в «Сюжете сейчас». Когда ИИ-мастер с каркасом начинает сессию, он представляет
ещё не представленных героев: первое вступление — как отряд встретился (120–200 слов, переход в первую сцену),
новичок посреди игры получает короткое появление перед следующим ходом мастера.

Ритм сессии у ИИ-мастера с каркасом: после вступления он ставит цель на вечер («Цель на этот вечер: …»),
на паузе после сводки сессии оставляет зацепку («В следующий раз: …»). Когда кампанию завершают, мастер
пишет эпилог: хронику для всех и судьбу каждого героя; эпилог сохраняется в `settings.epilogue`, герои и мир
остаются. В ваншоте мастер видит в инструкции, сколько ходов сыграно из примерно 30, и после 70% сводит историю
к финалу.

Чат нативный: игрок просто пишет, что делает или говорит герой, без выбора типа сообщения. Парсер сам
решает, действие это или реплика, а сообщение не про игру уходит во внеигровой чат. Отдельно есть только
переключатель «Шёпот мастеру»; префикс `//` по-прежнему сразу отправляет сообщение вне игры.

Действие игрока сначала разбирает парсер намерений (дешёвая модель: у Claude — отдельная быстрая, у других
провайдеров — модель мастера). Он сопоставляет цель и предмет с id, отклоняет оффтоп и попытки решать за чужого
героя, задаёт уточняющий вопрос, если не понял, и в бою оставляет одно действие и перемещение. Однозначную атаку
оружием сервер проводит сам, без модели; мастер её только описывает.

Память мастера: каждый ход мастер получает сводку кампании и несколько фрагментов правил и лора, найденных по репликам
игроков и месту действия (правила — `content/dnd5e-srd/data/rules.yaml`, лор — факты, локации и фракции пакета мира).
Сводку пишет дешёвая модель каждые `summary_every` сообщений (по умолчанию 30) и при паузе или конце сессии; шёпоты
в неё не попадают. Следующая сессия начинается с «Ранее в кампании…» по последней сводке.

Бой пошаговый: после броска инициативы ходит тот, чья очередь, остальные пишут только вне игры (`//`) или шёпотом.
На ход дано `turn_timeout_sec` (по умолчанию 300 с), потом герой «выжидает». Ходы существ сервер проводит сам
по профилю поведения шаблона: агрессивные сближаются и бьют самого раненого героя, трусливые бегут при потере хитов.
Когда существо убегает из ближнего боя, игрок получает кнопку атаки по возможности на `reaction_sec` (15 с).
Живой мастер закрывает ход героя или существа кнопкой «Пропустить ход».

Персонаж создаётся в комнате кампании: класс, происхождение, характеристики (стандартный набор, покупка очков
или 4d6), навыки и снаряжение. Сервер проверяет лист по правилам, затем героя одобряет мастер (или сразу,
если в кампании выбрана автоматическая проверка).

С туннелем пропишите его адрес в `PUBLIC_URL`, чтобы ссылки-приглашения вели наружу, и перезапустите `app`.
Первый вход — под Super Admin из `.env`; он заводит админов (`POST /api/admin/users`), админы создают кампании и приглашения.
Игроки регистрируются сами (имя и пароль от 6 символов; `OPEN_SIGNUP=0` закрывает регистрацию без приглашения).
Ссылка-приглашение запоминается, пока человек входит или регистрируется, а после входа он выбирает, кем играть:
готовым героем от владельца, копией героя из своего профиля или новым героем. Копия в кампании развивается
отдельно от героя в профиле. Владелец, который не ведёт игру сам, сразу занимает место игрока.
При старте сервер применяет миграции и импортирует базовый пакет SRD. Свой мир можно загрузить zip-архивом в админке (раздел «Пакеты»: сначала проверка, потом запись) или положить в `content/<id>/` и импортировать:

```
docker compose exec app python -m app.content import content/<id>
```

Разработка:

```
pip install -e ".[dev]"
pytest                                            # SQLite; TEST_DATABASE_URL=postgresql+asyncpg://… — на PostgreSQL
uvicorn app.main:app --reload                     # DATABASE_URL по умолчанию — SQLite-файл
alembic upgrade head                              # схема БД (DATABASE_URL)
python -m app.content validate путь/к/пакету --customs
```

API описан в `/docs` (OpenAPI). Протокол WebSocket — ТЗ, раздел 12: `auth` → `campaign.join` → `state.snapshot` → `message.send`;
в бою ещё `turn.changed`, `turn.pass`, `reaction.prompt` / `reaction.choose`, `message.notice`.
