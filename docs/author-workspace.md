# Пространство автора и повторно используемые приключения

Для кого: администраторы, которые готовят приключение один раз и запускают из него несколько независимых игр.

## Два пути

| | Обычное создание (`/new`) | Пространство автора (`/author`) |
| --- | --- | --- |
| Результат | Одна кампания, мир готовится по ходу игры | Опубликованная неизменяемая версия приключения |
| Мир | Создаётся лениво при входе героев | Готовится заранее: все места, участки, NPC, предметы и карты |
| Запуск | Сразу игра | Игра создаётся из библиотеки (`/games/new`), без новой генерации мира |
| Платная генерация | Во время игры | В авторском проекте, с бюджетом |

Старый путь не изменён: `/new`, `/c/:id`, `/c/:id/manage` работают как раньше и не требуют авторского проекта.

## Процесс

1. **Проект.** `POST /api/author/projects` создаёт `AuthorProject` и изолированный рабочий мир (`purpose = author_workspace`). Рабочий мир не попадает в игровые списки, приглашения, лобби и фоновое восстановление; героев и сессий в нём нет.
2. **Подготовка.** Этапы `lore → plot → geography → materialize → maps → validate` ставятся в очередь (`POST …/prepare`). У каждого запроса есть `request_key` и `expected_revision`; одинаковые входы дают одну работу, устаревший результат не перезаписывает свежий. После перезапуска сервера runner продолжает с сохранённого состояния.
3. **Правки.** Ручные формы и подтверждённые предложения ИИ идут через один валидатор (`POST …/edits`). Изменение имени карту не перестраивает; изменение частей, маршрутов и размещений помечает результаты устаревшими. Устаревшее нужно пересобрать или явно принять (`…/edits/accept-stale`).
4. **Проверка.** `POST …/validate` — детерминированная проверка текущей ревизии без модели. Любая последующая правка делает отчёт непригодным для публикации.
5. **Публикация.** `POST …/publish` создаёт `AdventureVersion` из типизированного снимка: логические ссылки вместо ID рабочего мира, без героев, чата и состояния исследования. Повтор с тем же `request_key` возвращает ту же версию; правка проекта v1 не меняет.
6. **Игра.** `POST /api/adventures/{version_id}/games` создаёт обычную игру с новыми ID. Повтор запроса с тем же ключом возвращает ту же игру; другие параметры при том же ключе — конфликт. Две игры из одной версии не делят состояния.

## Без спойлеров

Режим по умолчанию — `summary`: статусы этапов, расходы, коды ошибок. Полное содержимое и карты отдаются только по явному запросу (`?view=full`, `…/maps/{location_ref}`) и только владельцу. Список библиотеки содержит публичную сводку и никогда — снимок приключения.

## Границы полной подготовки

Готовятся все объявленные места и их участки, NPC с домом, ключевые предметы (в участке, в авторском контейнере или в руках NPC), носители сюжетных зацепок и порты маршрутов. Не обещается:

- содержимое, которое игроки создают действиями во время игры;
- условия появления NPC без исполняемого контракта: такой NPC блокирует публикацию.

## Перегенерация карты

Правка частей места (`edit_map`) помечает его layout, геометрию, размещения и порты маршрутов устаревшими. Этап `maps` (с `target_ref` места или без него — для всех устаревших) готовит новую карту отдельным кандидатом. Только когда все фазы кандидата готовы, он атомарно заменяет прежнюю карту: жители и ключевые предметы переезжают на новые места, производные объекты старой карты удаляются, сюжет и география указывают на кандидата. Неудачный кандидат удаляется, прежняя карта остаётся. Устаревший результат можно и явно принять как есть.

## Бюджет и повторный запуск

Перед платным вызовом резервируется верхняя оценка расхода. Не хватает бюджета — этап получает `blocked/budget_exhausted`, готовые результаты сохраняются. Расходы привязаны к работе (`llm_calls.author_job_id`); стоимость, которую провайдер не сообщил, показывается как неизвестная, а не нулевая. Повтор готового этапа не вызывает модель, пока не изменились входы или не запрошен новый вариант (`regenerate`).

## Переходы между участками

Маршрут соединяет конкретные участки (`loc_cave/part_crawl → loc_tunnels/part_junction`). Порт маршрута — клетки на проходимом полу участка; он виден на карте как выход с `route_ref`. Игрок выбирает его на карте (`map.traverse` с `route_ref`), мастер — инструментом `travel_route`. Сервер проверяет, что герои стоят в порту, маршрут открыт и не скрыт, отряд не разделён и бой не идёт, затем атомарно перемещает их. Обратная лестница или соседний выход маршрут не заменяют; у одностороннего маршрута нет обратного выхода. Переход не создаёт `state.links`.

## Известные ограничения первой версии

- Порт маршрута ставится на ближайшую к краю проходимую клетку участка, а не встраивается в Blueprint как проход: внутренние проходы комплекса не меняются.
- Для подготовки используется прежний `develop` с `here=False`; отдельного рефакторинга материализации нет.
