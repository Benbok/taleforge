# Выбор оружия и снаряжения игроком — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Делегирование — только если пользователь выберет superpowers:subagent-driven-development.

**Goal:** Игрок управляет оружием, щитом и доспехом во вкладке «Снаряжение», а сервер проверяет руки, стоимость действий, ход, облик и права доступа.

**Architecture:** Общая функция экипировки обслуживает мастер-инструмент и REST игрока. Сначала чистый расчёт всех снятий и стоимости, затем проверка оплаты и единая запись изменений с inverse. Сервер отдаёт свойства предметов и доступность следующего переключения: интерфейс использует тот же расчёт, что и серверная мутация.

**Tech Stack:** Python 3.11+, FastAPI, Pydantic, SQLAlchemy, pytest; React, TypeScript, Zustand, Vitest, Testing Library; штатный OpenAPI generator, graphify.

**Spec:** Исходное ТЗ пользователя «выбор оружия и снаряжения игроком в “Снаряжении” героя» и согласованные правки из этой беседы; их исполнимая фиксация — раздел «Правила и решения» ниже. Отдельный дизайн-документ для этого расширения существующего потока не требуется.

## Global Constraints

- Вне боя смена свободная. В бою смена возможна только при `economy.active(world, hero_id)`.
- Первое взаимодействие с оружием за ход бесплатно; каждое следующее требует действия `use_object`.
- Снятие каждого вытесняемого оружия — отдельное взаимодействие; взятие нового — ещё одно.
- Надевание и снятие щита требует действия, включая автоматическое вытеснение щита.
- Доспех в бою не надевается и не снимается; вне боя новая броня снимает предыдущую.
- Не более двух рук: одноручное оружие — одна, `two_handed` — две, щит — одна.
- Снятие и вытеснение оружия вызывает `release_weapon`; запрет `_can_handle_form` сохраняется.
- Черты «Быстрые руки» и «Двуручный боец», новые правила бросания/подбора и дополнительные слоты вне задачи.
- Известные 8 падений `unknown_parser`/`unparsed` не исправлять; не считать любое новое падение в этих файлах автоматически известным.
- Не включать чужие незакоммиченные изменения. На момент планирования изменены `app/tools/spells.py`, `tests/test_shillelagh.py`, `web/src/game/GridBoard.tsx`, `web/src/game/LocationMap.tsx`; перепроверить перед исполнением.

## Правила и решения

### Руки, порядок и стоимость

При взятии предмета сначала снять предметы того же исключающего слота: прежний доспех или прежний щит. Затем, если рук всё ещё больше двух, вытеснять другое оружие по стабильному порядку `inventory.id`; щит вытеснять последним. Новую вещь не вытеснять. `versatile` само по себе занимает одну руку: режим хвата вне задачи. Несколько экземпляров в строке `qty > 1` не означают несколько экипированных оружий.

Стоимость — сумма операций: каждое снятие/взятие оружия отдельно, каждое снятие/надевание щита отдельно. Все проверки выполняются до мутаций. В бою:

| Переход | Операции | Цена при свободном взаимодействии |
| --- | --- | --- |
| Пустые руки → меч | Взять меч | Бесплатно |
| Меч → пустые руки | Убрать меч | Бесплатно |
| Меч → лук | Убрать меч, взять лук | Бесплатное взаимодействие + 1 действие |
| Два одноручных → двуручное | Убрать два, взять одно | Бесплатное взаимодействие + 2 действия |
| Щит → пустая рука | Снять щит | 1 действие; взаимодействие остаётся |
| Старый щит → новый щит | Снять старый, надеть новый | 2 действия |
| Меч + щит → лук | Убрать меч, снять щит, взять лук | Бесплатное взаимодействие + 2 действия |

При недостатке действий составная смена целиком отклоняется. Нельзя бесплатно вытеснить щит двуручным оружием. Дополнительные действия от уже существующего Всплеска действий учитываются штатным ledger; не вводить жёсткий предел «одно платное взаимодействие за ход».

Существующее бросание оружия остаётся бесплатным и не расходует взаимодействие; этот план не добавляет кнопку бросания и не меняет подбор. Повторная установка текущего состояния — no-op после проверок доступа, предмета, хода и облика: без списания и без нового события экипировки.

### Доступность в интерфейсе

Чтобы не дублировать составной расчёт стоимости в TypeScript, добавить необязательное поле полного листа `equipment`:

```text
EquipmentState = {
  can_manage?: bool, in_combat: bool,
  changes: dict[inventory_id, EquipmentChangeView]
}
EquipmentChangeView = {
  allowed: bool, reason: str | None,
  action_cost: int, interaction_count: int,
  displaced_ids: list[str]
}
```

`changes[id]` описывает переключение в противоположное текущему `equipped` состояние. Неподходящие категории не получают кнопки. Причина и стоимость вычисляются сервером из общего планировщика; право `can_manage` определяется viewer, а не статусом «видит полный лист». В REST полного игрового листа `can_manage` всегда присутствует; в общем сокетном представлении его нет. При отсутствии `equipment` или viewer-specific права у старого/неполного ответа интерфейс перечитывает лист и до загрузки не разрешает мутации.

Текущее состояние доступности нужно обновлять при открытии вкладки и изменениях сцены/хода, включая трату действия другим способом. Использовать существующий REST листа, только пока вкладка открыта; отменять устаревшие запросы. Сокетный лист без viewer-specific поля `can_manage` не должен давать новые права.
