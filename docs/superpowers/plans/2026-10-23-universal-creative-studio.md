# Universal Creative Studio Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Разрабатывать универсальную RPG через законченные пользовательские узлы, начиная с героя и проверяя работающий результат после каждого узла.

**Architecture:** Шесть последовательных узлов объединяют UI, API, сохранение и проверки одного сценария. Первый узел даёт библиотеку/карточку, второй — уже играемое приключение. Схема создаётся в начале и развивается миграциями; окончательная уборка не откладывает запуск до конца разработки.

**Tech Stack:** Python 3.11+, FastAPI, Pydantic 2, SQLAlchemy async, SQLite/PostgreSQL, pytest; React19, TypeScript, React Query, Zustand, Vitest.

**Spec:** [Approved design and subsequent clarifications](../specs/2026-10-23-universal-creative-studio-design.md)

## Global Constraints

- Единая универсальная система, без классов, обязательных каталогов рас/заклинаний, клеточной тактики и короткого/длительного отдыха.
- Любой герой создаётся L1/xp0, включая создание непосредственно в кампании. Стартовый набор15/14/13/12/10/8 используется ровно один раз.
- Базовый герой живёт вне кампании и редактируется вручную или через чат с мастером. Ручное изменение характеристик — только перестановка фиксированного набора.
- В кампанию добавляется копия; созданный внутри кампании герой тоже отдельный игровой экземпляр. После создания ручное редактирование и чат-редактор карточки игрового героя недоступны.
- Повышение новичка до уровня группы происходит после создания/добавления копии; мастер выдаёт игровую прибавку, игрок распределяет очки в самой игре. Это не часть конструктора.
- Рост даёт2 очка за уровень, оба можно вложить в один стат; лимита уровня нет. Рост/события игровой копии никогда не меняют библиотечный оригинал.
- 6 характеристик,5 энергий; HP=10+CON+6*(L-1); проверки/урон/расход вычисляются, мастер трактует сохранённый результат.
- Один игровой шаг допускает ответ одного врага. Повтор не дублирует расход, урон, освоение, эффекты или XP. Каждому участнику полная одинаковая награда.
- Авторские версии и запуски изолированы. Секреты и спасения при0HP не попадают в публичный/голосовой рассказ.
- Новая ветка и новая БД с первого узла; старые игровые данные не переносим и не архивируем. Созданные в новой версии герои/кампании сохраняются при развитии следующих узлов: финального повторного сброса нет.
- Сохраняем авторизацию, память/поиск, учёт LLM и аудио. Чужие незакоммиченные изменения не переносим автоматически и не уничтожаем.
- Тесты используют ScriptedLLM; проверка качества живой модели фиксируется отдельно. После изменений кода — graphify update .

## Границы карточек и редактирования

Базовый библиотечный герой и игровой экземпляр имеют разные API-возможности, а не только разные кнопки. apply_hero_edit принимает только базового героя владельца; отправка game-character ID запрещена и вручную, и из чата. Чат не получает обходного пути через generic tool. Черновик создания в кампании можно уточнять до подтверждения; подтверждение всегда создаёт L1. Затем admit/catch-up — отдельное игровое событие с отдельным источником очков.

Игровые HP/энергия, предметы, эффекты, способности, XP и уровень меняются через игровые операции. Распределение новых level-up/catch-up очков — штатное действие внутри игры, не разрешение редактировать всю карточку. Изменения библиотечного героя после запуска не синхронизируются с копиями.

## Общие интерфейсы и владельцы

DTO вводятся в задаче, которая впервые использует их, а не все в первой задаче. Герой и его карточка — Tasks1–5; игровые профили/исходы — Tasks8–11; предметы/бой — Tasks13–16; рост — Tasks18–20.

Модуль app/rules/universal/contracts.py:
- AbilityKey = Literal["str","dex","con","int","wis","cha"]; EnergyKey исключает con.
- AbilityScores: закрытая модель шести положительных целых характеристик.
- HeroDescription(name="", identity, appearance="", personality="", capabilities=""); identity непустое.
- StartingAllocationProposal(abilities:AbilityScores, explanations:dict[AbilityKey,str]) — предложение мастера для любого нового героя L1. Ровно шесть значений15/14/13/12/10/8. Создание начинается с описания; для базового библиотечного героя после создания доступны ручная перестановка и чат-редактор. Готовый герой кампании эти редакторы не использует. Доработка черновика создания не является редактированием уже созданного игрового героя.
- UniversalSheet(schema_version=1, rules_version="universal.v1", level, xp, abilities, description, trained: list[str], unspent_points, budget). HeroBudget(initial_scores, growth_total, growth_allocations, unspent) хранится сервером: initial_scores — точная перестановка стартового набора, growth_allocations неотрицательны и вместе с unspent равны growth_total. Библиотечный базовый герой всегда L1/xp0/growth_total0; игрой заработанные или выданные при catch-up очки относятся только к игровой копии. Предметные/временные бонусы не становятся постоянным бюджетом.
- ActorResources(hp, energies: dict[EnergyKey,int], dead=False, stable=False, death_successes=0, death_failures=0).
- ActorDerived(hp_max, energy_max: dict[EnergyKey,int], ac, modifiers: dict[AbilityKey,int]).
- ItemStatus = Literal["common","rare","unique","epic"] с подписями обычный/редкий/уникальный/эпический. ItemProfile(id, revision, name, description, kind, rarity:ItemStatus, slot, use_conditions, action_profiles, defense_bonuses, effects, restoration); поля свойств валидируются по типу предмета. Количество и признак equipped относятся к экземпляру инвентаря.
- ProfileSpec(id, revision, attribute, kind, use_kind, base_dice, attack_bonus=0, damage_bonus=0, intensity, rarity, target_count, duration, resource_key, effects).
- EffectSpec(id, source_id, target_id, kind, value, clock, remaining, starts_at); kinds: damage, heal, check_bonus, defense_bonus, cannot_act, cannot_move, cannot_target, narrative.
- ResistanceSpec(source_attribute, attribute, difficulty, on_success, on_failure) — параметры отдельного эффекта, фиксируемые до броска; source_attribute управляет способностью, attribute задаёт защиту цели. difficulty вычисляется сервером как 10 + M(характеристика источника) из снимка действия; не произвольное число модели.
- EffectOutcome(effect_id, target_id, applied, natural, total, difficulty) — результат отдельного эффекта; успешная защита означает applied=False.
- ActionOutcome(status, success, natural, total, damage, cost, effect_outcomes, public_effects, private_effects); status: applied/denied/repeated/failed. success не заменяет результаты отдельных компонентов: попадание может нанести урон без наложения дополнительного эффекта. Эффект профиля может содержать ResistanceSpec; шаблон эффекта задаёт проверку, конкретная сложность фиксируется для попытки до броска.
- DomainError(code, message) — предсказуемый отказ без технических исключений в публичном тексте.

Числа внутри Python — int; коэффициенты — точные рациональные значения, не float. На wire неограниченно растущие значения (характеристики, HP, энергии, XP, уровень, урон) — десятичные строки; натуральные d20, число целей и счётчики 0..3 — обычные числа. Frontend использует BigInt для вычисления/сравнения счётчиков и форматирует строку без Number(). Это техническое решение для отсутствия старого предела уровня и потери точности, а не новая игровая механика.

ProfileSpec:
- HPmax = 10 + CON + 6*(level-1). При CON14 уровни 1/5/10/20/100 дают HP 24/48/78/138/618. Рост CON на 2 увеличивает максимум HP на 2; рост уровня без изменения CON — на 6. Для энергии сохраняется отдельная формула из дизайна.
- Урон: Dbase = roll(base_dice) + M(attribute) + 2*(level-1) + damage_bonus; D = max(1, floor(intensity * rarity * max(0, Dbase))) до защиты и иммунитетов. attack_bonus применяется только к попаданию; крит удваивает только базовые кубики. Коэффициент 2 — кандидат прототипа.
- Дополнительный эффект проверяется отдельно от попадания: например, cannot_move от лозы допускает защиту ловкостью, а не запрещает действия. Успешное сопротивление не отменяет урон и не возвращает цену попытки. Сопротивление: d20 + M(защитная характеристика цели) >= 10 + M(характеристика способности источника). Бонус подготовки не добавляется автоматически. Применимость, характеристики и сложность фиксируются до броска; натуральная 20 в сопротивлении не получает автоматически правило критического попадания.
- kind: damage/heal/control/defense/narrative; intensity: light/normal/strong => 1/2,1,2.
- use_kind: ability/weapon_basic. Только сервер формирует weapon_basic из действительно экипированного оружия; модель не может объявить новую магию бесплатной базовой атакой.
- Базовые профили: small=1d4, standard=1d6, heavy=1d8; heavy требует условия применения, сохраняемого мастером. Не принимать из ответа модели произвольное 100d100.
- rarity предмета: common/rare/unique/epic. Прежнюю шестиступенчатую шкалу не использовать. Коэффициенты и бюджеты этих четырёх статусов ещё не определены: зафиксировать конфигурацию для прототипа перед реализацией числовых профилей и проверить предварительно в Task 8 и расширенно в Task 21. Для действия без предмета коэффициент редкости равен 1; статус не присваивается самому герою автоматически.
- target_count >=1, duration >=1; для MVP цена умножается на оба значения. На разовой атаке duration=1.
- Составной профиль оплачивает каждый числовой компонент: полная цена = базовая цена * target_count * duration * numeric_component_count. Основной damage/heal/control/defense — один компонент; каждый дополнительный числовой эффект — ещё один. Повествовательные детали не дают числовых компонентов бесплатно.
- Control без урона: один конкретный запрет из EffectSpec; defense/check_bonus: величина 1/2/3 для light/normal/strong. Heal использует ту же базовую формулу как восстановление, ограниченное недостачей.
- Narrative сохраняет факт; при отсутствии числового эффекта не даёт скрытого бесплатного бонуса.
- Числовые операции компилируются сервером из профиля и броска. Поле EffectSpec.value из предложения модели проверяется против допустимого бюджета; resolve_action не принимает произвольный готовый HP-урон, восстановление энергии или set_hp в обход профиля/расходника.
- Произвольное название допустимо; общий контракт числовых операций закрыт. Дополнение нового названия не требует Python-обработчика.
- Подготовка: +2, если соответствующий опыт/приём уже подтверждён; иначе 0. Это выбранное значение первого прототипа, а не дополнительное пользовательское решение.


## Сохранённые числовые предложения прототипа

- Урон складывает кубики, модификатор,2*(L-1) и предметный бонус; интенсивность/редкость применяются один раз. Базы1d4/1d6/1d8 — предложения, а не запрет выдумывать названия.
- Интенсивности.5/1/2, цена L*ceil(3*q*q), множители числа целей/длительности/компонентов. Запрет дополнительного эффекта бесплатно сохраняется.
- Подготовка+2 — предложение для обычных проверок; сопротивление не получает её автоматически. Натуральные1/20 для атак, крит удваивает только базовые кубики.
- Обычная атака не тратит ресурс специального приёма; сильная интенсивность/дополнительный эффект не бесплатны. Броня: тело/щит/совместимые слоты; одинаковый defense_bonus_key не суммируется.
- Для критической неудачи вредное последствие сохраняется; прежнее предложение резервного эффекта-1 к следующей проверке при отсутствии выбранного HP-вреда остаётся видимым допущением прототипа.
- Коэффициенты четырёх статусов предметов и некоторые правила частичного освоения составного умения ещё требуют явного числового/сценарного решения перед их включением; не выдавать их за отдельно утверждённые значения.
- Полный баланс не блокирует карточку из узла1. Предварительная проверка чисел обязательна перед игрой узла2, расширенная — при развитии в узле4.
