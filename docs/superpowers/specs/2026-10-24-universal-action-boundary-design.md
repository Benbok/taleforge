# Universal action boundary

Approved direction: user requested the systemic action-boundary refactor before Node3, after failures of firefly illumination and a mundane torch check.

The model proposes semantic intent; server code compiles it into existing bounded profiles. Canonical categories are narrative, ordinary_check, ability, weapon_attack, world_denial and unsupported. Costs, numeric effect values, ownership and target scope remain authoritative server rules. Existing saved admissions and immutable receipts remain readable; no data reset or broad frontend redesign.

One reusable validator is called during preparation and again inside atomic resolution. Its registry is also sent to the model. Initially only the already implemented immediate actor/self effects are executable; scheduled, scene-duration, conditional and arbitrary-item effects remain unavailable until later plan nodes. Unsupported mechanics must never become fictional prohibitions.

Failures carry stable categories/codes and public Russian explanations: invalid proposal, unsupported capability, access/target/stale-state issues, insufficient resources, failed roll and internal/provider failure. Private model deliberation and world secrets never reach public failure views. Technical failures are rendered deterministically, not narrated as changes in the world.

Validate and compile before persisting an executable admission. Allow at most one constrained repair of a model proposal per source, persist the attempt budget, and never repair by removing requested effects or weakening world laws. Retries reuse valid prepared actions and existing Event receipts. Old invalid admissions are revalidated; they are not blindly replayed. A narration failure never repeats committed effects.

Public source-message metadata distinguishes a handled refusal from success; the UI must not show a success checkmark for an unsupported or rejected action. Ordinary free checks never consume energy or teach an ability. Physical weapon attacks still require a saved equipped weapon.

Verification uses deterministic providers, including the actual torch and firefly proposal shapes, malformed/hidden targets, repair exhaustion, insufficient resources, ordinary checks, known abilities, paid profiles and restart/replay. No live paid model calls are needed. Existing unrelated user frontend edits are preserved and excluded from commits.
