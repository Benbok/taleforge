# ТЗ: AI-Мастер для текстовых ролевых игр

Sep 27, 2026 · @Arty

## 1. Цель и границы проекта

Платформа для текстовых ролевых игр в чате: мастер и игроки могут быть людьми или ИИ-агентами, механику считает сервер, а мир ограничен базой правил и сеттингом кампании.

**Входит в MVP:**

- ИИ-мастер и 2–6 живых игроков в одной кампании.
- Приглашения по ссылке, чат через WebSocket.
- Пошаговый режим для боя и свободный режим для исследования.
- Изменение состояния персонажей только через инструменты мастера.
- Кампания на несколько сессий с памятью между ними.
- Локальный запуск на машине владельца с доступом через туннель.

**Сменный мир.** Игра не привязана к одному сеттингу: автор может полностью прописать свой мир, базу знаний и данные и подключить их пакетом (раздел 3.2). Неизменна только механика, которая зависит от кода.

**Следующие этапы:** живой мастер, ИИ-игроки, слепая генерация сеттинга, голосования при уходе игрока, другие каналы (Telegram, Discord). На старте клиент только веб, язык только русский.

**Глоссарий**

| Термин | Значение |
| --- | --- |
| Кампания (комната) | Долгая игра с одним сеттингом, составом и персонажами. Живёт неделями. |
| Сессия | Один сеанс игры внутри кампании: от старта до паузы или завершения. |
| Место (seat) | Роль в кампании: мастер или игрок. Занимается человеком или агентом. |
| Ядро правил | Общая для всех кампаний механика и шаблоны: характеристики, предметы, эффекты, существа. |
| Сеттинг | Мир конкретной кампании. Публичная вводная видна всем, остальное только мастеру. |
| Намерение | Структурированная версия реплики игрока: кто, что делает, с чем и чем. |
| Событие | Запись в журнале о любом изменении состояния: урон, эффект, предмет, перемещение. |
| Пакет сеттинга | Сменный мир в виде данных: лор, база знаний, шаблоны и расширения правил. Подключается к кампании, пишется автором мира без кода (раздел 3.2). |

## 1.1. Главный принцип: ИИ — голос, приложение — мир

ИИ-мастер и ИИ-игрок — исключительно творческие личности: они описывают, говорят и отыгрывают. Вся механика, логика и правила — это код и данные приложения. Любое состояние (хиты, эффекты, инвентарь, позиции, отношение NPC, живы ли существа) хранится в базе данных и меняется только событиями, а не текстом модели.

| Задача | ИИ (мастер или игрок) | Приложение |
| --- | --- | --- |
| Описать сцену и атмосферу | Да | — |
| Говорить за NPC и за своего героя | Да | — |
| Понять, что хочет игрок | Относит текст к типу действия из правил | Проверяет, что такой тип есть |
| Какой навык и какая сложность | Выбирает сложность из шкалы пакета, если её нет в данных | Таблица «действие → навык», сложность из шаблона объекта, отношения NPC или шкалы сложностей пакета |
| Попал ли удар, сколько урона | — | Движок правил |
| Кто появился в сцене | Описывает появление | Таблица встреч локации и бюджет встречи |
| Что делает монстр в бою | Описывает | Профиль поведения из шаблона и правила морали |
| Как NPC относится к героям | Озвучивает | Отношение в `state`, меняется по результатам проверок |
| Что выпало с врага | Описывает находку | Таблица добычи |
| Хиты, эффекты, инвентарь, позиции | Никогда не хранит и не помнит | База данных, каждое изменение — событие в журнале |
| Что было раньше | Пересказывает | Журнал событий и реестр мира |

**Творческая часть ИИ-мастера ограничена четырьмя вещами:** стиль повествования, характер реакций NPC и существ, манера общения и выбор сложности проверки. Сложность тоже выбирается из базы знаний: из шаблона объекта, отношения NPC или шкалы сложностей пакета (по умолчанию шкала SRD: 5, 10, 15, 20, 25, 30). Механику мастер только применяет к среде и существам и ничего не выдумывает.

**Если текст модели и база данных расходятся, права база.** Текст переписывается, база не трогается.

**ИИ-игрок** решает, чего хочет его герой, и говорит за него. Его реплика проходит тот же парсер, те же правила и те же проверки, что и у человека. Инструментов у него нет, а о мире он знает только то, что есть в листе его персонажа и в уровнях знаний.

**Что это добавляет в данные:** поле `behavior` в `creature_templates` (агрессивный, трусливый, защитник, порог бегства), таблицы `encounter_tables` для локаций, `skill_map` (тип действия → навык), `trap_templates`, поле `dc` у шаблонов объектов и локаций.

## 2. Роли и права доступа

Права разделены на два уровня: роль на платформе и место в кампании. Управлять комнатой и читать скрытые данные мастера — это разные права, и владелец кампании по умолчанию получает только первое.

**Роли на платформе**

| Роль | Что может |
| --- | --- |
| Super Admin | Глобальные настройки, ключи провайдеров, создание админов. Через API скрытые данные кампаний не читает. |
| Admin | Создаёт кампании, приглашает игроков, запускает генерацию сеттинга, загружает и обновляет пакеты сеттинга (раздел 3.2). Видит только свои кампании. |
| Player | Входит в кампании по приглашению. Видит чат, своего персонажа и то, что ему открыто. |

**Места в кампании.** Мастер и игрок — это места, а не типы пользователей. Каждое место занимает человек (`user_id`) или агент (`agent_config_id`). Серверу всё равно, кто сидит на месте: оба работают через один и тот же интерфейс сообщений и инструментов, поэтому место можно передать агенту и обратно без перезапуска.

**Матрица доступа внутри кампании**

| Действие | Владелец | Мастер | Игрок |
| --- | --- | --- | --- |
| Пригласить или исключить участника | да | нет | нет |
| Поставить сессию на паузу, завершить | да | да | через голосование |
| Читать скрытый лор и тайны сюжета | нет | да | нет |
| Видеть параметры всех существ | нет | да | по уровню знаний |
| Видеть лист своего персонажа | — | да | да |
| Видеть листы других персонажей | нет | да | только публичную часть |
| Шёпот мастеру | — | получает | да |

Владелец кампании, который сам играет, — это одновременно «владелец» и «игрок». Скрытые данные хранятся в отдельной таблице, и сервер отдаёт их только месту мастера. Интрига защищена кодом, а не честным словом.

## 3. Архитектура и стек

Сервер — единственный источник правды: он хранит состояние, считает механику и решает, кому что показать. Модели (мастер, парсер, ИИ-игроки) получают собранный контекст и возвращают текст и вызовы инструментов.

Клиент общается только с WebSocket-шлюзом. Ключи провайдеров живут на сервере, игроки к моделям напрямую не обращаются.

**Стек**

| Слой | Инструмент | Зачем |
| --- | --- | --- |
| Бэкенд | Python 3.12, FastAPI, Uvicorn | Асинхронность, нативные WebSocket, удобно для LLM-кода |
| Схемы | Pydantic v2 | Намерения, аргументы инструментов, события — всё валидируется |
| БД | PostgreSQL 16, SQLAlchemy 2, Alembic | JSONB для статов и эффектов, миграции |
| Поиск по правилам и лору | pgvector | Достаём только релевантные фрагменты правил и сеттинга |
| Горячее состояние | Redis | Активная сессия, очередь ходов, pub/sub между воркерами, блокировки |
| Модели | LiteLLM | Один интерфейс к Claude, Gemini и локальным моделям через Ollama |
| Фронтенд | React, TypeScript, Vite, Zustand, Tailwind | Чат, виджеты, всплывающие карточки |
| Авторизация | JWT + одноразовые токены приглашений | Вход по ссылке без сложной регистрации |
| Развёртывание | Docker Compose | Один запуск поднимает сервер, БД и Redis |
| Доступ извне | Cloudflare Tunnel или ngrok | Игра на своей машине, друзья подключаются по ссылке |
| Тесты | pytest, pytest-asyncio | Отдельно тестируется движок правил без моделей |

**Абстракция провайдеров.** Для каждого места-агента задаётся конфигурация: провайдер, модель, температура, персона. Мастеру по умолчанию ставится сильная модель с хорошим творческим письмом: качество повествования важнее цены хода. Парсеру и сводкам хватит дешёвой и быстрой, ИИ-игрокам — средней. Смена провайдера — это правка конфигурации, а не кода. Провайдер выбирается при создании кампании и для каждого места отдельно из трёх вариантов: Claude, Gemini или локальная модель. Тестовые сценарии мастера (раздел 7.1) прогоняются на каждом поддерживаемом провайдере.

**Локальный запуск.** `docker compose up` поднимает всё на машине владельца, туннель выдаёт публичный адрес, ссылки-приглашения строятся от него. Переезд на VPS — тот же Compose без туннеля.

## 3.1. Расширяемость

Проект строится как модульный монолит: одно приложение, но каждая подсистема живёт в своём пакете и общается с остальными через явные интерфейсы. Новая фича добавляется новым модулем или регистрацией, а не правкой ядра.

**Структура кода**

```
app/
  core/          # кампании, места, сцены, события, права
  rules/
    base.py      # интерфейс RulesEngine
    dnd5e/       # первая реализация правил
  content/
    dnd5e-srd/   # YAML-шаблоны: предметы, эффекты, существа, опасности
  tools/         # реестр инструментов мастера
  agents/        # мастер, парсер, ИИ-игрок, генератор сеттинга
    prompts/     # шаблоны промптов (Jinja2)
  gateway/       # web (WebSocket), позже Telegram, Discord
  api/           # REST: кампании, приглашения, админка
```

**Точки расширения**

| Что меняется | Как устроено | Что нужно для новой фичи |
| --- | --- | --- |
| Система правил | Интерфейс `RulesEngine`: проверки, атака, урон, инициатива, производные статы | Новая реализация или правка модуля `dnd5e` |
| Контент и сеттинги | Пакеты YAML: базовый пакет правил и пакеты сеттинга (раздел 3.2). Загрузчик валидирует и импортирует в БД | Добавить файлы или свой пакет, запустить импорт |
| Инструменты мастера | Реестр: Pydantic-схема + обработчик + права. Описание для модели генерируется из схемы | Зарегистрировать новый инструмент |
| Реакции на события | Внутренняя шина доменных событий (`character.damaged`, `item.given`), подписчики | Новый подписчик: достижения, логи, интеграции |
| Промпты | Файлы шаблонов с версией | Правка файла, без изменения кода |
| Каналы клиента | Адаптеры шлюза с общим интерфейсом | Новый адаптер: Telegram, Discord |
| Модели | LiteLLM + `agent_configs` | Новая запись в конфигурации |
| Медиа (после MVP) | Подписчик шины событий + провайдер генерации | Модуль media: иллюстрации сцен и портреты героев, музыка и фон по настроению сцены |
| Экспериментальные фичи | Флаги на уровне кампании | Включить флаг для нужной кампании |

**Правила против поломок**

- Кампания привязана к `ruleset_id` и версии. Обновление правил не ломает идущие кампании: переход на новую версию — отдельная миграция по желанию владельца.
- Характеристики и ресурсы хранятся в `JSONB` и описаны в `stat_definitions`. Новый стат — это запись в данных, а не миграция схемы.
- Протокол WebSocket версионирован, клиент игнорирует неизвестные поля и события.
- Набор тестовых сценариев для мастера (реплика → ожидаемые вызовы инструментов) прогоняется при каждой смене промпта или модели, чтобы правки не ломали поведение незаметно.

**Стартовые правила: D&D 5e SRD**

Первая реализация `RulesEngine` переносит механику из System Reference Document 5-й редакции. SRD распространяется под лицензией CC BY 4.0: использовать можно, но нужна атрибуция, и брать можно только то, что входит в SRD, без закрытых торговых марок, сеттингов и существ из основных книг.

| Механика D&D | Куда ложится в системе |
| --- | --- |
| 6 характеристик и модификаторы | `stat_definitions`, производные статы считает `RulesEngine` |
| Проверка: d20 + модификатор против сложности | `roll_check` |
| Преимущество и помеха | Флаги в `roll_check`, источники — эффекты |
| Класс брони, попадание, урон по оружию | `resolve_attack` + `item_templates` |
| Хиты, спасброски, смерть и стабилизация (смерть по SRD окончательная, воскрешение — только если его даёт пакет сеттинга) | Ресурсы персонажа + `roll_check` |
| Состояния (ослеплён, отравлен, сбит с ног) | `effect_templates` |
| Действие, бонусное действие, перемещение, реакция | Лимит действий за ход в парсере и оркестраторе |
| Инициатива | `set_scene_mode` |
| Урон от падения и среды | `hazard_templates` |

Для MVP берутся базовые классы, оружие, броня, состояния и часть монстров из SRD. Механика заклинаний, подклассов и повышения уровней входит в движок MVP (раздел 7.2), а сами заклинания и подклассы приходят из пакета сеттинга как база знаний. Дальше правила меняются правкой модуля `dnd5e` или форком в свой `RulesEngine`.

## 3.2. Пакеты сеттинга: свой мир как данные

Игра не привязана к одному миру. Сеттинг — это **пакет контента**: папка с паспортом, данными и текстами, которую можно написать целиком самому и подключить к кампании. Код задаёт, *как* считается механика, пакет задаёт, *что* существует в мире и как это называется. Первый такой пакет — «Эхо Левиафанов» (`content/echo-leviathans/`), его соглашения взяты здесь за основу.

**Три слоя**

| Слой | Что в нём | Кто меняет | Как |
| --- | --- | --- | --- |
| Движок правил (код) | Бросок d20 и сложность, атака и урон, экономия действий, инициатива, состояния SRD, отдых, время и длительности, часы мира, интерпретатор модификаторов и триггеров, журнал событий, права и видимость | Разработчик | Правка модуля `rules/dnd5e` или новая реализация `RulesEngine` |
| Базовый пакет правил (данные) | `dnd5e-srd`: классы, оружие, броня, монстры, состояния из SRD 5.1 | Разработчик | YAML-пакет, общий для всех кампаний |
| Пакет сеттинга (данные) | Мир, база знаний и всё, что мир добавляет или меняет в правилах поверх базы | Автор мира | Свой YAML-пакет, подключается к кампании |

**Что автор мира может задать без кода**

| Область | Виды записей | Пример из «Эха Левиафанов» |
| --- | --- | --- |
| Лор и база знаний | `lore_fact` (с уровнем знания и видимостью), `faction`, `location_template`, `campaign_secret`, длинные тексты `source_docs` | Канон мира, фракции, карта поясов |
| Новые характеристики, ресурсы, шкалы, валюты | `stat_definition`, словарь подписей для виджетов | Скверна 0–6, Перемена, эхо, ФК вместо золотых |
| Эффекты, опасности, часы мира | `effect_template`, `hazard_template`, `clock` | Уровни Скверны, налёт, Сила Резонанса |
| Существа, предметы, добыча, встречи | `creature_template` (можно поверх SRD через `srd_ref`), `item_template`, `loot_table`, `price_index`, `encounter_table` | Выводки роя, хитиновое оружие |
| Создание персонажа | `origin` вместо расы, `lineage`, `class`, `subclass`, правила кампании (потолок уровня, запрет рас и классов SRD) | Только люди, происхождения, потолок 15 |
| Особые силы и заклинания | `echo_technique`, `spell_template` | Голод и Отклик, заклинания SRD |
| Подача | Тон, стиль повествования, глоссарий, исключённые темы, публичная вводная, готовые персонажи | — |

**Что требует кода.** Новый тип броска или проверки, новый `op` в языке модификаторов, новый тип триггера, новая структура хода, новое событие движка (например, «Испытание Порога» или «Порог тишины»). Такие места пакет помечает `{op: custom, text: "..."}`: это заявка разработчику, а не работающая механика. **В игру такая запись не попадает:** механика должна быть прописана как исполняемое правило, иначе её нет. Запись с `custom` не может иметь статус `canon`, импортируется только в тестовые кампании и в игровой кампании не видна ни движку, ни мастеру, в том числе как описание. Правило раздела 8 «новые механики запрещены» относится к мастеру во время игры, а не к автору пакета: пакет расширяет правила, но только теми средствами, которые движок умеет исполнять.

**Паспорт пакета (`pack.yaml`)**

| Поле | Назначение |
| --- | --- |
| `id`, `name`, `version` | Идентификатор, название, версия по semver |
| `ruleset`, `ruleset_base` | Движок и базовый пакет правил, например `dnd5e` и `srd-5.1` |
| `depends` | Другие пакеты с версиями (для надстроек над чужим миром) |
| `engine` | Минимальная версия движка и список нужных возможностей (`ops`, `triggers`, `events`) |
| `excludes` | Что из базы выключено: виды, классы, предметы SRD |
| `level_cap`, `languages` | Потолок уровня, языки контента |
| `dc_scale` | Шкала сложностей для мастера; без неё — шкала SRD 5–30 |
| `license` | Лицензия мира и атрибуция SRD |
| `source_docs` | Длинные тексты канона, из которых нарезается база знаний |

**Формат записей** — как в пакете «Эхо Левиафанов»: файл `{kind, items}`, `id` вида `kind.snake_case`, уникальный в пакете; общие поля `name`, `description`, `status` (`canon` или `proposal`), `doc`, `tags`, `srd_ref`; ссылки в полях `*_ref` и `*_refs`; всё вычисляемое записывается через язык модификаторов и триггеров, а не текстом.

**Две схемы.** Движок владеет **ядровой схемой**: список видов записей (каждый вид — таблица из раздела 4), обязательные поля и язык модификаторов. Неизвестный вид или `op` — ошибка импорта. Пакет может добавить **свою схему** поверх, строже ядровой: например, «Эхо Левиафанов» требует у локации поле `belt`. Дополнительные поля записи ядро не отбрасывает, они ложатся в JSONB и доступны мастеру как описание.

**Импорт пакета**

1. **Схема.** Каждая запись проверяется ядровой схемой и схемой пакета.
2. **Ссылки.** Все `*_ref` разрешаются внутри пакета и его зависимостей, `srd_ref` — по базовому пакету правил.
3. **Совместимость.** Движок проверяет `engine`: если пакету нужна возможность, которой нет, импорт останавливается с перечнем.
4. **Отчёт.** Счётчики по видам, список `custom`-модификаторов (механика, которую движок пока не исполняет, — список работ для разработчика), записи в статусе `proposal`. Запись `canon` с `custom` — ошибка импорта.
5. **Запись в БД.** Строки шаблонов пишутся с `pack_id` и `version`. Старые версии не удаляются.
6. **База знаний.** Факты лора и `source_docs` нарезаются на фрагменты с эмбеддингами (pgvector) и помечаются видимостью: публичное, знание персонажа по уровню, только мастер.

Валидатор пакета запускается и локально (`tools/validate.py`), и сервером при импорте, с одной и той же ядровой схемой. Загружать и обновлять пакеты может только Admin (и Super Admin), игроки свои миры не загружают. В MVP пакет импортируется командой из папки `content/`, загрузка архива через админку — позже.

**Пакет и кампания**

- Кампания привязана к пакету и его версии так же, как к `ruleset_id`. Новая версия пакета не меняет идущие кампании, переход — отдельная миграция по желанию владельца.
- При создании кампании `campaign_secret` и стартовые записи реестра копируются в кампанию. Дальше мир кампании живёт своей жизнью (`add_lore`, `create_quest`, события), а пакет остаётся неизменным образцом.
- В игровых кампаниях используются только записи `canon`. Записи `proposal` доступны в тестовых кампаниях, чтобы обкатать черновики до утверждения.
- Слепая генерация сеттинга (раздел 8) работает внутри выбранного пакета: генератор пишет кампанию из его шаблонов и лора. Если пакета нет, берётся базовый `dnd5e-srd`.
- Подписи виджетов, названия валют и глоссарий берутся из пакета, виджеты и расчёты остаются из ядра (раздел 10).

**Что добавляется в систему:** таблица `content_packs` (`id`, `version`, `manifest JSONB`, `checksum`, `imported_at`, `import_report JSONB`); поля `pack_id`, `pack_version` во всех таблицах шаблонов и в `campaigns`; таблица `lore_sections` для базы знаний (`pack_id`, `campaign_id`, `body`, `embedding`, `visibility`, `knowledge_level`); команда импорта и общая с пакетами ядровая схема в `app/content/schema/`.

## 4. Модель данных

Данные делятся на три слоя: ядро правил (только чтение, общее для всех), кампания (сеттинг, места, персонажи) и живое состояние (сообщения, события, сводки). Любое изменение персонажа идёт через запись в `events` и обновление карточки в одной транзакции.

**Ядро правил** — наполняется разработчиком, версионируется

| Таблица | Назначение | Ключевые поля |
| --- | --- | --- |
| `rule_sections` | Текст правил, нарезанный на фрагменты для поиска | `id`, `title`, `body`, `embedding`, `version` |
| `stat_definitions` | Какие характеристики и ресурсы есть у персонажа | `code`, `name`, `min`, `max`, `widget_type` |
| `item_templates` | Все предметы, оружие, броня | `id`, `name`, `category`, `stats JSONB`, `rarity` |
| `effect_templates` | Баффы, дебаффы, ранения, состояния | `id`, `name`, `modifiers JSONB`, `default_duration`, `stackable` |
| `creature_templates` | Шаблоны существ и NPC | `id`, `name`, `stats JSONB`, `abilities`, `loot_table` |
| `hazard_templates` | Урон от среды: падение, огонь, яд | `id`, `name`, `formula`, `params_schema` |

**Кампания**

| Таблица | Назначение | Ключевые поля |
| --- | --- | --- |
| `users` | Учётные записи | `id`, `name`, `platform_role` |
| `campaigns` | Кампании (комнаты) | `id`, `owner_id`, `name`, `status`, `ruleset_version`, `public_intro` |

| `seats` | Места мастера и игроков | `id`, `campaign_id`, `role`, `occupant_type`, `user_id`, `agent_config_id`, `delegated_from` |
| `characters` | Персонажи | `id`, `seat_id`, `name`, `stats JSONB`, `resources JSONB`, `public_bio` |
| `character_effects` | Наложенные эффекты | `character_id`, `effect_template_id`, `stacks`, `expires_turn`, `source_event_id` |
| `inventory` | Предметы персонажа | `character_id`, `item_template_id`, `display_name`, `qty`, `equipped` |
| `entities` | NPC, монстры, локации, объекты кампании | `id`, `kind`, `name`, `template_id`, `state JSONB`, `location_id` |
| `knowledge` | Что персонаж знает о сущности | `character_id`, `entity_id`, `level` |

**Живое состояние**

| Таблица | Назначение | Ключевые поля |
| --- | --- | --- |
| `sessions` | Сеансы игры | `id`, `campaign_id`, `started_at`, `ended_at`, `end_reason` |
| `scenes` | Режим и очередь текущей сцены | `campaign_id`, `mode`, `turn_order`, `current_seat_id`, `round` |
| `messages` | Весь чат | `id`, `session_id`, `seat_id`, `kind`, `visible_to`, `content`, `intent JSONB` |

## 5. Игровой цикл

У сцены два режима, и переключает их мастер инструментом `set_scene_mode`. В любом режиме мастер отвечает на пакет реплик, а не на каждое сообщение, иначе агент и люди будут перебивать друг друга.

|  | Свободный режим | Пошаговый режим |
| --- | --- | --- |
| Когда | Исследование, диалоги, отдых | Бой, погоня, напряжённые сцены |
| Кто пишет | Все, в любом порядке | Только игрок, чей сейчас ход |
| Когда отвечает мастер | Все активные игроки написали или прошло окно сбора (по умолчанию 60 с) | После каждого хода |
| Порядок | Нет | Очередь инициативы, считает движок правил |
| Таймаут | Окно сбора | Время хода (по умолчанию и максимум 5 мин, игра идёт вживую), затем действие по умолчанию («выжидает») |

**Типы сообщений**

| Тип | Кто видит | Идёт мастеру |
| --- | --- | --- |
| Действие персонажа | Все | Да, через парсер |
| Реплика персонажа (прямая речь) | Все | Да |
| Шёпот мастеру | Автор и мастер | Да, помечено как тайное |
| Внеигровой комментарий (префикс `//`) | Все | Нет |
| Повествование мастера | Все или адресно | — |
| Системное (бросок, событие, голосование) | Все | Как результат инструментов |

**Жизненный цикл сессии:** старт (владелец или мастер) → игра → пауза или завершение → автоматическая сводка сессии. При следующем старте мастер открывает сессию коротким «Ранее в кампании…» по сводке.

Пока мастер обрабатывает ход, ввод для этого хода закрыт. Реплики в свободном режиме копятся в очередь следующего пакета.

## 5.1. Создание персонажей

Игрок получает персонажа двумя путями: собирает своего в конструкторе по правилам или берёт готовый вариант. Оба пути заканчиваются проверкой мастера. Соответствие правилам проверяет сервер, а мастер оценивает только историю и соответствие сеттингу.

&#91;embedded content: создание персонажа · два пути, одна проверка\]

Мастер может вернуть персонажа на доработку с комментарием. Доработка идёт в конструкторе, даже если персонаж был взят из готовых.

**Настройки при создании кампании**

| Параметр | Варианты | По умолчанию |
| --- | --- | --- |
| Способ создания | Свой, готовый, оба | Оба |
| Стартовый уровень | 1–20 | 1 |
| Генерация характеристик | Стандартный набор (15, 14, 13, 12, 10, 8), покупка очков (27), броски 4d6 без меньшего | Стандартный набор |
| Доступные виды и классы | Из пакета контента, лишние можно исключить | Все из SRD |
| Стартовое снаряжение | Набор класса и предыстории, золото на покупку | Набор |
| Проверка мастером | Обязательна, автоодобрение после проверки правил | Обязательна |
| Старт сессии без персонажей у всех | Запрещён, разрешён | Запрещён |

Броски 4d6 делает сервер один раз и пишет в журнал, чтобы нельзя было перебрасывать до хорошего результата.

**Конструктор**

1. Вид (раса).
2. Класс.
3. Характеристики — способом из настроек кампании.
4. Предыстория.
5. Навыки и владения.
6. Снаряжение.
7. Имя, внешность, публичное описание и личная история.

После каждого шага сервер пересчитывает производные величины (хиты, класс брони, модификаторы, бонус мастерства) и возвращает ошибки. Черновик сохраняется, к нему можно вернуться позже.

**Помощник.** Игрок может описать героя словами («хитрый полурослик-вор, бывший уличный музыкант»), и ИИ заполнит шаги конструктора. Игрок правит и подтверждает. Помощник заполняет только поля конструктора, и проверка правил та же самая.

**Готовые варианты**

| Источник | Кто создаёт | Особенность |
| --- | --- | --- |
| Пакет контента | Разработчик | Базовые сборки на SRD, общие для всех кампаний |
| Кампания | Владелец или живой мастер в конструкторе | Сборки для конкретной кампании |
| Генерация под сеттинг | ИИ-мастер при создании кампании | Истории связаны с миром, проходят ту же валидацию |

Взятый вариант копируется в `characters` и скрывается для остальных игроков кампании. Имя, внешность и историю можно менять сразу, механику — только через конструктор.

**Проверка мастером.** Мастер получает лист и историю, одобряет или возвращает с комментарием. ИИ-мастер может тайно связать историю персонажа с сюжетом: связь пишется в `campaign_secrets`, игрок её не видит. Личная история видна только игроку и мастеру, публичное описание — всем.

**Статусы персонажа:** черновик → на проверке → одобрен → в игре → погиб или ушёл из истории.

**Особые случаи**

| Ситуация | Поведение |
| --- | --- |
| Игрок присоединился после старта | Тот же путь, мастер решает, как ввести героя в сцену |
| Место занимает ИИ-игрок | Берёт готовый вариант или собирает через помощника, характер задаёт Admin (раздел 5.2) |
| Персонаж погиб | Новый персонаж тем же путём, уровень по настройке кампании |

**Что добавляется в систему**

- Таблица `character_templates`: `id`, `campaign_id` (пусто для пакета контента), `source`, `data JSONB`, `taken_by_seat_id`.
- В `characters`: `status`, `creation_method`, `template_id`, `private_backstory`. В `campaigns`: `creation_rules JSONB`.
- `RulesEngine`: `creation_options`, `validate_character`, `derive_stats`, `roll_ability_scores`.
- Инструменты мастера: `review_character` (решение и комментарий), `create_pregen`.
- WebSocket: клиент → `character.draft.update`, `character.submit`; сервер → `character.validation`, `character.reviewed`.

## 5.2. Состав кампании: мастер, размер отряда и ИИ-игроки

Закладывается в архитектуру сразу, включается по этапам (раздел 13). Места уже устроены так, что их может занять человек или агент (раздел 2), поэтому новых сущностей почти не нужно.

**Мастер.** При создании кампании Admin выбирает, кто займёт место мастера:

| Вариант | Что происходит |
| --- | --- |
| Сам Admin | Место мастера занимает Admin: панель мастера, те же инструменты через команды (раздел 7), доступ к `campaign_secrets`. Как владелец он при этом не становится игроком |
| ИИ-агент | Admin выбирает провайдера и модель (Claude, Gemini, локальная) и стиль ведения из пакета сеттинга. Скрытые данные Admin не видит (раздел 2) |

Смена позже возможна в обе стороны: живой мастер передаёт место агенту и обратно (раздел 11). Если мастер — Admin, слепая генерация сеттинга не нужна, он пишет или правит его сам (раздел 8).

**Рекомендуемый размер отряда.** При создании кампании сервер предлагает число игроков по правилам D&D и выбранной сложности кампании:

- Правила встреч и бюджет опасности SRD рассчитаны на отряд из 4 персонажей. Это рекомендация по умолчанию, допустимо 3–6.
- Сложность кампании (`campaigns.difficulty`: лёгкая, обычная, сложная, смертельная) — настройка кампании, её шкала и описание берутся из пакета сеттинга. Она сдвигает бюджет встреч и добычи, а рекомендация показывает, сколько персонажей нужно, чтобы кампания проходилась с такой сложностью без постоянной гибели отряда.
- Пакет сеттинга может задать свою рекомендацию (`pack.yaml`: `party_size: {min, recommended, max}`).
- Число реальных персонажей всегда попадает в бюджет встреч (раздел 8.1): если отряд меньше рекомендованного, встречи ослабляются по правилам, а не остаются рассчитанными на четверых.

**ИИ-игроки на пустых местах.** Если живых игроков меньше рекомендованного, Admin может занять пустые места ИИ-игроками. Сервер предлагает недостающие роли в отряде (например, нет лечения или разведчика) и соответствующие классы, Admin соглашается или выбирает сам.

Персонаж ИИ-игрока создаётся тем же путём, что у человека (раздел 5.1): готовый вариант или конструктор через помощника, та же проверка правил и мастера. Для отыгрыша у него, как и у любого персонажа, есть **характер**:

| Что задаёт отыгрыш | Откуда |
| --- | --- |
| Класс, происхождение (вид) и предыстория | Лист персонажа, данные пакета |
| Черты характера, идеал, привязанность, слабость | Таблицы предыстории пакета (как в SRD): выбираются Admin из списка или случайно |
| Манера речи и темперамент | Короткое описание персоны, выбирается из пресетов пакета или пишется Admin |
| Цель героя в кампании | Выбирается Admin или предлагается мастером при проверке персонажа |

Из этих полей сервер собирает персону агента-игрока. Характер влияет только на то, *что герой хочет и как говорит*: реплика агента проходит тот же парсер, правила и проверки, что у человека, инструментов у него нет, а знает он только свой лист и открытое ему в `knowledge` (раздел 1.1). Живой игрок может позже занять место ИИ-игрока и получить его персонажа (раздел 11).

**Что добавляется в систему:** поля `campaigns.difficulty`, `campaigns.party_size_recommended`; в `characters` — `personality JSONB` (черты, идеал, привязанность, слабость, манера речи, цель), заполняется и у персонажей людей и передаётся мастеру для отыгрыша; в `agent_configs` — `persona_source` (ссылка на персонажа); `pack.yaml` — `party_size`, `difficulty_levels`, пресеты персон; мастер создания кампании в админке: выбор мастера, сложность, рекомендация, заполнение пустых мест.

## 6. Обработка намерений игрока

Парсер превращает свободный текст в проверяемое намерение, но не решает, получится ли действие. Судить о возможности поступка — работа правил и мастера: попытка перепрыгнуть пропасть и падение — это часть игры.

**Как работает**

1. Парсер (дешёвая быстрая модель со структурированным выводом) получает реплику, лист персонажа и список видимых в сцене сущностей с их `id`.
2. Возвращает JSON по схеме ниже, сервер валидирует его через Pydantic.
3. Ссылки вроде «гоблин слева» сопоставляются с `id` сущностей. Если однозначно не выходит — игроку уходит уточняющий вопрос.
4. Заявленный игроком результат («и я убиваю его одним ударом») отбрасывается: игрок заявляет попытку, исход определяет сервер.
5. Готовое намерение уходит оркестратору, исходный текст сохраняется в чате как есть.

**Схема намерения**

```json
{
  "kind": "action",
  "character_id": "char_17",
  "actions": [
    {
      "verb": "attack",
      "target_id": "ent_goblin_2",
      "instrument_id": "inv_sword_01",
      "manner": "с разбега, целясь в ноги"
    }
  ],
  "speech": "За короля!",
  "outcome_claim_removed": true,
  "confidence": 0.86
}
```

`kind`: `action`, `speech`, `question_to_master`, `whisper`, `ooc`. `verb` — из закрытого списка глаголов ядра правил (атаковать, осмотреть, использовать, переместиться, говорить и т. д.), всё непонятное попадает в `custom` и решается мастером.

**Когда реплика отклоняется**

| Причина | Реакция |
| --- | --- |
| Оффтоп, не относится к игре | Предложить перенести во внеигровой чат `//` |
| Попытка управлять чужим персонажем | Вернуть с пояснением |
| Больше действий, чем разрешено за ход | Взять первые, остальное вернуть |
| Не удалось понять (низкий `confidence`) | Уточняющий вопрос |
| Предмета нет в инвентаре | Пропустить, пусть мастер обыграет («рука нащупывает пустые ножны») |

## 7. Инструменты мастера

Мастер меняет мир только вызовами инструментов, а числа считает сервер. Текст «ты потерял 5 здоровья» без вызова ничего не меняет, а любой вызов оставляет запись в `events` и привязан к конкретному персонажу.

&#91;embedded content: один ход · от реплики до повествования\]

Мастер может вызвать несколько инструментов подряд (лимит — 8 за ход) и только после этого пишет повествование, опираясь на полученные результаты.

**Список инструментов**

| Инструмент | Аргументы | Что делает сервер |
| --- | --- | --- |
| `get_scene` | — | Возвращает сущности сцены, режим, очередь |
| `get_character` | `character_id` | Актуальный лист: статы, ресурсы, эффекты, инвентарь |
| `lookup_rules` | `query` | Поиск по фрагментам правил |
| `lookup_template` | `kind`, `query` | Поиск шаблона предмета, эффекта, существа, опасности |
| `roll_check` | `character_id`, `stat`, `difficulty`, `reason` | Бросает кубики с учётом модификаторов, возвращает успех и степень. Сложность — только значение из шаблона или шкалы сложностей пакета |
| `resolve_attack` | `attacker_id`, `target_id`, `instrument_id` | Попадание, урон по шаблону оружия, списание здоровья |
| `apply_hazard` | `target_id`, `hazard_template_id`, `params` | Урон от среды по формуле: падение с высоты, огонь, яд |
| `apply_effect` | `target_id`, `effect_template_id`, `duration?` | Накладывает бафф, дебафф или ранение |
| `remove_effect` | `target_id`, `effect_id` | Снимает эффект |
| `use_item` | `character_id`, `inventory_id`, `target_id?` | Применяет предмет по его шаблону |
| `give_item` / `take_item` | `character_id`, `item_template_id`, `qty`, `display_name?` | Изменяет инвентарь |
| `spawn_entity` | `creature_template_id`, `name`, `location_id` | Добавляет NPC или монстра в сцену |
| `update_entity` | `entity_id`, `patch` | Меняет нарративные поля: отношение, настроение, статус |
| `move` | `character_ids`, `location_id` | Перемещает персонажей |
| `reveal_knowledge` | `character_id`, `entity_id`, `level` | Открывает игроку сведения о сущности |
| `set_scene_mode` | `mode`, `participants` | Включает пошаговый или свободный режим, бросает инициативу |
| `whisper` | `seat_id`, `text` | Личное сообщение одному игроку |

**Контракт вызова**

- Ответ всегда `{ok, result, event_id}` или `{ok: false, error}`. Ошибка возвращается модели, и она исправляет вызов.
- Несуществующий `template_id` — ошибка. Именно это не даёт мастеру придумать предмет или бафф.
- Мастер никогда не передаёт число урона напрямую: только шаблон и параметры (высота падения, сложность проверки), и параметры ограничены схемой.
- Каждое изменение сразу рассылается клиентам как `character.updated`, виджеты обновляются до появления текста.
- В повествовании мастер размечает сущности как `[[ent_goblin_2|гоблин]]`. Сервер проверяет, что `id` существует, иначе снимает разметку.

**Живой мастер** пользуется теми же инструментами через панель и команды в чате (`/атака`, `/эффект`, `/проверка`). **ИИ-игроки** инструментов не имеют: они пишут реплики как люди и проходят через тот же парсер.

## 7.1. Надёжность вызова инструментов и состояния

Модель ошибается предсказуемо: пишет урон текстом и забывает вызвать инструмент, выдумывает цель, путает `id`, забывает снять эффект. Поэтому надёжность строится не на промпте, а на слоях, где каждую ошибку ловит код. Главный принцип: всё, что можно решить без модели, решается без модели.

&#91;embedded content: надёжный ход · 7 слоёв проверки\]

Типовые действия идут от маршрутизатора сразу в валидатор, минуя модель. Модель участвует только в творческих решениях и в повествовании.

**Слои защиты**

| Слой | Что делает | Какую ошибку ловит |
| --- | --- | --- |
| Маршрутизатор механик | Типовые намерения переводит в вызовы сам, по таблице | Забытая атака или использование предмета |
| Раздельные фазы | В фазе решения модель только вызывает инструменты (низкая температура). В фазе повествования изменяющих инструментов нет | Урон или лут, описанный без вызова |
| Динамические схемы | Поля `target_id`, `instrument_id`, `effect_template_id` каждый ход получают список реально доступных значений | Выдуманные цели и предметы |
| Валидатор | До выполнения проверяет: цель жива и в сцене, дальность, есть ли действие в этом ходу, есть ли предмет | Нарушение правил |
| Контракт намерения | Проверяет, что на каждое намерение есть обязательный вызов или явный отказ | Проигнорированное действие игрока |
| Аудитор повествования | Сверяет текст с событиями хода: числа, смерть, предметы, эффекты, попадание или промах | Текст противоречит механике |
| Транзакция хода | Все события хода фиксируются вместе с повествованием. Сбой — откат всего хода | Полусделанный ход |

**Маршрутизатор: что решает код, а что модель**

Модель только относит слова игрока к типу действия, который есть в правилах, и описывает результат. Навык, сложность, урон, действия существ и реакции NPC определяют правила и данные.

| Намерение | Что делает модель | Что делает код |
| --- | --- | --- |
| Атака оружием по видимой цели | Только описывает результат | `resolve_attack` |
| Использование предмета | Только описывает | `use_item` по шаблону предмета |
| Перемещение | Только описывает | `move` с проверкой зон |
| Осмотреть, найти, взломать, убедить | Только описывает | Навык по `skill_map`, сложность из шаблона объекта или отношения NPC, `roll_check` |
| Нестандартное действие («раскачаться на люстре и сбить врага») | Относит к типу действия из правил: импровизированная атака, толчок, проверка Акробатики | Параметры и бросок по правилам этого типа |
| Ход монстра | Описывает | Действие выбирает профиль поведения шаблона и правила морали |
| Реакция NPC | Озвучивает | Изменение отношения по результату проверки |
| Ловушки и опасности | Описывает | Ловушка — сущность из `trap_templates`: сложность обнаружения, спасбросок, урон |
| Появление врагов | Описывает | Таблица встреч локации и бюджет встречи |

Если парсер не уверен в типе действия, намерение идёт модели, а не в автоматическую ветку.

**Контракт намерения.** На каждое действие игрока мастер обязан либо вызвать нужный инструмент, либо явно отказать через `cancel_action(reason)`: цель скрылась, дверь уже открыта. Для тривиальных действий есть `auto_success(reason)`. Молчание запрещено: если действие не закрыто ни вызовом, ни отказом, фаза решения повторяется. Оба инструмента добавляются в список из раздела 7, отказы видны в журнале.

**Состояние монстров и NPC**

- Существо существует для механики только после `spawn_entity`. Создаётся экземпляр из шаблона с текущими хитами, эффектами и ресурсами. Монстра, который только упомянут в тексте, атаковать нельзя: валидатор вернёт ошибку с подсказкой вызвать `spawn_entity`.
- Состояние экземпляра хранится в `entities.state`: текущие и максимальные хиты, эффекты, ресурсы способностей, зона, отношение к героям, жив или нет.
- Всё, что зависит от времени, ведёт сервер: длительность эффектов, спасброски от смерти, концентрация, восстановление способностей, отдых. Модель не отвечает за снятие эффектов.
- При нуле хитов сервер сам меняет статус. Мёртвая сущность не действует и пропадает из списка целей атаки, но остаётся доступной для осмотра и обыска.
- Существа остаются в своих локациях между сценами и сессиями. Раненый гоблин, сбежавший из боя, при следующей встрече будет раненым, если по правилам не успел отдохнуть.
- В MVP вместо сетки — зоны дальности: вплотную, близко, далеко. Дальность оружия и заклинаний проверяется по зонам, для текстовой игры этого хватает.

**Что мастер видит каждый ход.** Сервер строит компактную таблицу сцены из БД. Модель никогда не держит числа в памяти и не берёт их из истории чата, только из этой таблицы.

```
СЦЕНА: Склеп · бой · раунд 3 · ход: Тарен
ent_gob_1  Гоблин-лучник  хиты 4/7    далеко   [отравлен: 1 ход]
ent_gob_2  Гоблин          мёртв
char_17    Тарен            хиты 18/24  вплотную действие: есть, бонусное: есть
```

**Обработка ошибок**

- Ошибка валидатора возвращается модели с причиной и допустимыми вариантами. После 2 неудачных повторов ход упрощается: код выполняет действие по умолчанию из маршрутизатора или фиксирует `cancel_action`.
- Аудитор нашёл расхождение — повествование перегенерируется с указанием ошибки, механика не пересчитывается.
- Каждый вызов имеет ключ идемпотентности: повтор после сбоя сети не спишет урон дважды.
- Каждое событие хранит обратную дельту, поэтому владелец может откатить последний ход при явной ошибке мастера.

**Наблюдаемость и тесты**

- Трассировка каждого хода: намерение, контекст, вызовы, результаты, повествование, срабатывания аудитора. Полный просмотр доступен только в тестовых кампаниях, чтобы не раскрывать секреты игры.
- Набор сценариев: состояние сцены + реплика → ожидаемые вызовы. Метрики: доля ходов со всеми нужными вызовами, доля ошибок валидатора, срабатывания аудитора. Прогоняется при каждой смене модели или промпта.
- Сценарии пополняются из реальных ошибок: плохой ход в тестовой кампании сохраняется как новый тест одной кнопкой.

## 7.2. Время, реакции, скрытые броски, уровни и заклинания

Решения Arty от 2026-09-27. Всё ниже — механика движка, мастер только вызывает инструменты.

**Игровое время.** Движок ведёт часы и календарь кампании (`campaigns.game_time`, календарь и названия месяцев — из пакета сеттинга). Длительности эффектов, отдых, восстановление способностей, часы мира и «успел ли раненый гоблин отдохнуть» считаются по этим часам. В бою время идёт раундами (6 секунд), вне боя его двигает мастер инструментом `advance_time(duration, reason)` по шагам из данных (минуты, часы, дни). Короткий и долгий отдых — инструмент `rest(character_ids, kind)`: движок проверяет условия SRD, двигает время и восстанавливает ресурсы. Прерывание отдыха — событием.

**Реакции в пошаговом бою.** Когда у персонажа возникает право на реакцию (враг выходит из досягаемости, по нему попадают и у него есть Щит), движок ставит ход на паузу и отправляет игроку кнопку с вариантами реакций и таймером 15 секунд. Нет ответа — реакция не используется. Реакции монстров и NPC выбирает профиль поведения шаблона без паузы. Одна реакция за раунд, учёт — в движке.

**Скрытые броски.** Проверки, результат которых персонаж знать не должен (Внимательность, Скрытность, Проницательность, поиск ловушек, пассивные значения), бросаются с флагом `hidden`. Результат видят только мастер и журнал, игрок получает только последствия в повествовании. Какие проверки скрытые, задаёт таблица в данных (`skill_map.hidden`), а не мастер. После сессии владелец может открыть журнал скрытых бросков для разбора.

**Рост уровней — по вехам.** Опыт не считается. Мастер вызывает `grant_level(character_ids, reason)` на сюжетной вехе, движок проверяет потолок уровня пакета и открывает игроку шаг повышения в конструкторе (хиты, умения, заклинания). Вехи кампании можно заранее описать в `campaign_secrets`. Решение пишется в журнал.

**Заклинания — механика движка, контент из базы знаний.** Движок в MVP поддерживает ячейки заклинаний, подготовку и известные заклинания, концентрацию, спасброски и атаки заклинаниями, ритуалы. Сами заклинания и списки классов — записи пакета (`spell_template`: круг, школа, время накладывания, дистанция в зонах, компоненты, длительность, концентрация, эффект на языке модификаторов). Мастер накладывает заклинание NPC и существ инструментом `cast_spell(caster_id, spell_template_id, target_ids, slot_level)`, игроки — через намерение. Заклинание, которого нет в пакете, не существует.

**Новые инструменты** (дополняют список раздела 7): `advance_time`, `rest`, `grant_level`, `cast_spell`. Новые события WebSocket: сервер → `reaction.prompt`, клиент → `reaction.choose`.

## 8. Ограничения мастера и слепая генерация сеттинга

Мастер ничего не создаёт словами. Любой персонаж, монстр, NPC, предмет, локация и эффект появляется в игре только как запись в реестре мира, созданная инструментом из шаблона приложения. Свободен мастер только в подаче: как описать, как говорит NPC, какой в зале запах.

| Мастер решает сам | Только через данные приложения |
| --- | --- |
| Описание, атмосфера, погода, запахи | Персонажи игроков (раздел 5.1) |
| Слова и манера речи NPC | Монстры и NPC: `spawn_entity` из шаблонов по таблицам встреч |
| Подача событий: в каком порядке и как рассказать | Предметы и лут: таблицы добычи и `item_templates` |
| Имя и внешность при создании сущности | Локации: карта сеттинга и `location_templates` |
| Отнесение нестандартного действия к типу из правил | Навыки, урон, эффекты — движок правил |
| Выбор сложности проверки, когда её нет в шаблоне объекта или отношении NPC — только из шкалы сложностей пакета, с причиной в журнале | Шкала сложностей (dc\_scale) и таблицы сложностей типовых задач — данные пакета |
| Характер реакций NPC и манера общения | Изменение отношения NPC — по результату проверки |
| — | Действия существ в бою — профили поведения |
| — | Факты о мире, квесты, фракции: `add_lore`, `create_quest` |
| — | Новые механики и характеристики — мастеру запрещены полностью; расширять правила может только пакет сеттинга средствами движка (раздел 3.2) |

**Слепая генерация сеттинга**

1. Владелец создаёт кампанию и отвечает на 4–5 вопросов генератора: жанр и атмосфера, тон (героический, мрачный, комедийный), стартовая ситуация, желаемая длина, темы, которые нужно исключить.
2. Агент-генератор создаёт сеттинг и записывает его в `campaign_secrets`: скрытый лор, фракции, NPC, карту локаций, сюжетные нити и тайны.
3. Каждое существо и предмет сеттинга привязывается к шаблону ядра. Сервер проверяет все `template_id` и возвращает генератору ошибки, пока привязка не будет полной.
4. Генератор отдельно пишет `public_intro` — вводную, которую видят все, включая владельца.
5. Владелец видит только свои ответы и вводную. Скрытая часть доступна лишь месту мастера.

Если мастер — человек, он видит и редактирует `campaign_secrets` сам или пишет сеттинг вручную. Исключённые темы из шага 1 попадают в системную инструкцию мастера как жёсткие ограничения на всю кампанию.

## 8.1. Реестр мира: нет записи — нет сущности

Всё, с чем можно взаимодействовать, живёт в реестре и имеет `id`. Модель может называть в тексте только то, что есть в реестре сцены, а создать новое — только инструментом из шаблона приложения. Сказанное однажды становится каноном: мир не меняется от ответа к ответу.

**Каталог сущностей**

| Тип | Откуда шаблон | Как появляется | Что задаёт мастер |
| --- | --- | --- | --- |
| Персонаж игрока | Конструктор или готовый вариант | Только через создание персонажа | Ничего, только изменения через инструменты |
| Монстр | `creature_templates` (SRD) | `spawn_entity` | Выбор шаблона, имя экземпляра |
| NPC | `creature_templates`: стражник, торговец, жрец, бандит и другие блоки NPC из SRD | `spawn_entity`; ключевые NPC — генератором сеттинга при создании кампании | Имя, характер, мотивы (сохраняются в `state`) |
| Предмет | `item_templates` | `give_item`, лут по `loot_table` существа | Название и описание, свойства — нет |
| Локация | `location_templates`: таверна, пещера, склеп, лес | Карта сеттинга или `create_location` в её границах | Описание, связи с соседними локациями |
| Эффект, способность, заклинание | `effect_templates`, шаблоны класса | Только через инструменты механики | Ничего |
| Факт о мире, квест, фракция | Сеттинг кампании | `add_lore`, `create_quest` | Текст факта, после записи неизменен |

**Декорации.** Фон без механики (дождь, толпа на рынке, трещина в стене) описывать можно, но у него нет `id`, и механически с ним взаимодействовать нельзя. Если игрок хочет что-то сделать с декорацией (поднять камень, сесть за стол), мастер сначала регистрирует её инструментом по подходящему шаблону, например «импровизированное оружие» из SRD, и только потом разрешает действие.

**Как это проверяется**

1. **Контекст.** Мастер видит только реестр текущей сцены и шаблоны, которые вернул `lookup_template`. Весь каталог в промпт не попадает, поэтому выдумывать «по памяти о D&D» не из чего.
2. **Схемы.** Во все поля с `template_id` и `entity_id` подставляется список допустимых значений на этот ход (раздел 7.1).
3. **Аудитор реестра.** После повествования сервер извлекает из текста имена, существ, предметы и места. Всё, чего нет в реестре сцены или что не размечено `[[id|…]]`, возвращает мастеру на исправление. Описание не может обещать свойств, которых нет у шаблона: «пылающий клинок» при обычном мече — ошибка.
4. **Вопросы о правилах.** Мастер отвечает только через `lookup_rules` со ссылкой на найденный фрагмент. Если правила нет — ответ «по правилам не определено» и решение общей проверкой характеристики, которое пишется в журнал.
5. **Вопросы о мире.** Ответ берётся из сеттинга и `knowledge` персонажа. Если факта нет, мастер может добавить его через `add_lore` — дальше он неизменен и доступен в следующих ходах.

**Баланс вместо произвола**

- `spawn_entity` в бою проверяет бюджет встречи: сумма опасности существ против уровня и реального размера отряда по правилам D&D с поправкой на сложность кампании (раздел 5.2). Превышение — отказ с подсказкой.
- `give_item` вне таблиц добычи ограничен бюджетом сокровищ по уровню отряда и требует причины в журнале.
- Генератор сеттинга при создании кампании работает через те же инструменты и проверки. Скрытый мир тоже целиком состоит из записей реестра, а не из свободного текста.

**Что добавляется в систему:** таблицы `location_templates`, `quests`, `lore_facts`; инструменты `create_location`, `add_lore`, `create_quest`; аудитор реестра как часть аудитора повествования из раздела 7.1.

**Настройка модели против галлюцинаций:** низкая температура в фазе решения, структурированный вывод, в системной инструкции разрешено отвечать «не знаю» и «такого здесь нет», а каждое срабатывание аудитора пишется в метрики и пополняет набор тестов.

## 9. Память кампании

Полный лог хранится в БД всегда, но мастеру каждый ход собирается свежий контекст из шести частей. Цифры (здоровье, инвентарь, эффекты) никогда не берутся из сводки — только из БД на момент хода.

**Сборка контекста мастера** (сверху вниз, от постоянного к свежему)

| Часть | Источник | Как часто меняется |
| --- | --- | --- |
| Системная инструкция: роль, правила поведения, исключённые темы | Код + настройки кампании | Никогда |
| Релевантные фрагменты правил | `rule_sections`, поиск по намерению | Каждый ход |
| Сеттинг: краткая выжимка + фрагменты по текущей локации | `campaign_secrets` | Редко |
| Сводка кампании | `summaries` | Раз в N ходов |
| Текущее состояние: сцена, персонажи, эффекты | `scenes`, `characters`, `entities` | Каждый ход |
| Последние ходы (по умолчанию 20 сообщений) и новое намерение | `messages` | Каждый ход |

Постоянные части идут первыми, чтобы работало кэширование промпта у провайдера и ход стоил дешевле.

**Сводка** обновляется дешёвой моделью каждые 30 сообщений и в конце сессии. Она структурирована: активные квесты, ключевые события, NPC и отношения с ними, открытые сюжетные нити, обещания и долги. Предыдущая сводка + новые сообщения → новая сводка, старые версии сохраняются.

## 10. Интерфейс

Экран — чат в центре, панель отряда и сцены слева, лист своего персонажа справа. На телефоне панели сворачиваются во вкладки над чатом.

**Виджеты.** Набор виджетов определяется ядром правил, а не сеттингом: у каждой записи в `stat_definitions` есть `widget_type` (полоса, число, список, счётчик). Сеттинг может только переименовать и перекрасить их через словарь подписей: «мана» станет «эфиром», но это тот же ресурс с тем же виджетом.

**Живые статусы** берутся из реальной стадии обработки хода, а не из таймера:

| Стадия на сервере | Что видят игроки |
| --- | --- |
| Парсер разбирает реплику | «Мастер слушает…» |
| Сборка контекста | «Мастер вспоминает…» |
| Вызов `roll_check` или `resolve_attack` | «Мастер бросает кубики…» |
| Генерация повествования | «Мастер описывает…» |

**Семантическая разметка и уровни знаний.** Слова вида `[[id|текст]]` становятся кликабельными. По клику клиент запрашивает карточку сущности, и сервер отдаёт только то, что открыто этому персонажу в `knowledge`:

| Уровень | Что видно |
| --- | --- |
| 0 — видел | Имя и внешнее описание |
| 1 — наслышан | Описание, известные повадки |
| 2 — изучил | Видимые характеристики: примерное здоровье, оружие |
| 3 — знает всё | Полная карточка без секретов сюжета |

Поле ввода показывает, чей сейчас ход, и имеет переключатели: действие, прямая речь, шёпот мастеру, внеигровой комментарий.

## 11. Офлайн и голосование

Голосование запускается не сразу при обрыве связи, а после периода ожидания: секундный лаг не должен останавливать игру.

1. Соединение пропало → статус «переподключается», ожидание 60 секунд. В пошаговом режиме ход игрока в это время пропускается.
2. Не вернулся за 60 секунд → статус «офлайн» и голосование среди оставшихся живых игроков.
3. Варианты: передать персонажа ИИ, передать другому живому игроку (выбирается кто), поставить кампанию на паузу.
4. Решение простым большинством. Ничья или 2 минуты без решения → пауза.
5. Если игрок вернулся во время голосования, оно отменяется.
6. Вернувшийся игрок получает персонажа обратно в начале следующего хода и короткую сводку пропущенного.

**Особые случаи**

| Ситуация | Поведение |
| --- | --- |
| Остался один живой игрок | Решает сам, без ожидания большинства |
| Ушёл живой мастер | Голосование: ИИ-мастер подхватывает или пауза |
| Ушли все игроки | Пауза без голосования |
| Персонаж под управлением ИИ | Агент получает лист персонажа и пометку «играть осторожно, не принимать необратимых решений» |

Замещение хранится в поле `delegated_from` места, поэтому в журнале видно, кто управлял персонажем в каждый момент.

**Как сделано (этап 8, 2026-09-29).** Код — `app/gateway/presence.py`. Ожидание переподключения и срок голосования
настраиваются в `settings` кампании: `reconnect_grace_sec` (60), `vote_timeout_sec` (120). Ход героя в бою
пропускается не мгновенно, а через `away_skip_sec` (5): перезагрузка страницы — не уход. Вариант «передать ИИ»
появится с ИИ-игроками (этап 9); до тех пор голосуют между «отдать другому игроку» и «пауза». Игрока-замену
хранит `seats.stand_in_user_id`, он пишет за героя, передавая `as_seat`, и видит его лист без личной предыстории.
ИИ-мастер на месте ушедшего живого мастера: `occupant_type = agent`, `delegated_from` — живой мастер. Пауза сессии
возвращает всех героев хозяевам. Сводку пропущенного пишет дешёвая модель ИИ-мастера; при живом мастере — без
модели: сколько пропущено и последнее повествование.

## 12. Протокол WebSocket

Все сообщения — JSON в одном конверте с порядковым номером. При переподключении клиент присылает последний полученный `seq`, и сервер досылает пропущенное.

```json
{ "type": "message.new", "campaign_id": "c_42", "seq": 1083, "payload": { } }
```

**Клиент → сервер**

| Событие | Назначение |
| --- | --- |
| `auth` | JWT при подключении |
| `campaign.join` | Вход в кампанию, в ответ `state.snapshot` |
| `message.send` | Реплика с типом: действие, речь, шёпот, `ooc` |
| `turn.pass` | Пропустить ход |
| `vote.cast` | Голос |
| `entity.inspect` | Запрос карточки по клику на разметку |
| `master.tool` | Вызов инструмента живым мастером |
| `ping` | Проверка связи |

**Сервер → клиент**

| Событие | Назначение |
| --- | --- |
| `state.snapshot` | Полное состояние, видимое этому участнику |
| `message.new` | Новое сообщение чата |
| `message.rejected` | Реплика отклонена парсером, с причиной |
| `master.status` | Стадия обработки хода для живых статусов |
| `turn.changed` | Чей сейчас ход, таймер |
| `character.updated` | Изменение листа персонажа, со ссылкой на `event_id` |
| `entity.card` | Карточка сущности по уровню знаний |
| `presence.changed` | Онлайн, переподключается, офлайн |
| `vote.started` / `vote.ended` | Голосование |
| `session.paused` / `session.ended` | Пауза и завершение |

Сервер фильтрует каждое событие по получателю: шёпоты, скрытые данные мастера и чужие закрытые поля никогда не уходят в чужой сокет.

## 13. Требования, этапы и открытые вопросы

**Нефункциональные требования**

- Обычный ход обрабатывается до 15 секунд, статус обновляется на каждой стадии.
- Ключи провайдеров хранятся только на сервере, в переменных окружения.
- Скрытые данные фильтруются на сервере, клиент не получает их даже в скрытом виде.
- Каждое обращение к модели пишется в `llm_calls` с токенами и стоимостью. У кампании есть лимит расходов, его задаёт Admin; жёсткого значения по умолчанию нет.
- Движок правил покрыт тестами без моделей: одинаковый seed кубиков даёт одинаковый результат.

**Этапы разработки**

1. **Ядро правил в виде данных.** Модуль `dnd5e` и пакет контента из SRD: характеристики, шаблоны, формулы. Без этого нечего подключать к мастеру.
2. **Каркас.** Авторизация, приглашения, кампании, чат через WebSocket, запуск через Docker Compose и туннель.
3. **ИИ-мастер.** Инструменты, движок правил, журнал событий, один провайдер через LiteLLM. Сеттинг пока пишется вручную.
4. **Парсер намерений и режимы сцены.** Пошаговый режим, очередь, таймауты.
5. **Память.** Сводки, сборка контекста, поиск по правилам.
6. **Интерфейс.** Виджеты, разметка, уровни знаний, живые статусы.
7. **Офлайн и голосования.**
8. **Живой мастер и ИИ-игроки** (выбор мастера при создании кампании, рекомендация размера отряда, ИИ-игроки с характером — раздел 5.2; модель данных закладывается с этапа 1).
9. **Слепая генерация сеттинга.**
10. **Генерация картинок и музыки.** В MVP игра только текстовая. Позже — иллюстрации сцен, портреты героев и фоновая музыка по месту и настроению сцены (бой, исследование, отдых). Генерация идёт отдельным модулем по событиям сцены и не влияет на механику; стиль задаёт пакет сеттинга.

**Открытые вопросы**

Открытых вопросов нет. Первый набор классов и монстров определяет пакет «Эхо Левиафанов».

**Закрытые вопросы (2026-09-27):** провайдер — на выбор Claude, Gemini или локальная модель; клиент на старте только веб; язык только русский; до 6 игроков; играющий владелец сохраняет права паузы и исключения; время, реакции, скрытые броски, уровни и заклинания — раздел 7.2; пакеты сеттинга загружает только Admin — раздел 3.2; живой мастер и ИИ-игроки — этап 8, модель данных сразу (раздел 5.2); игра вживую, ход до 5 минут; смерть по SRD; в MVP только текст, картинки и музыка — этап 10; мастеру — сильная творческая модель, лимит расходов задаёт Admin.
