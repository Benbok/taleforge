# Локальные звуковые эффекты

Модель: Stable Audio 3 Small-SFX. SFX запускается отдельным сервисом `sfx` вместе с обычным `docker compose up -d --build`. Приложение не ждёт скачивания весов: во время подготовки генерация недоступна, остальные функции работают.

## Первый запуск

1. Принять условия доступа к [модели](https://huggingface.co/stabilityai/stable-audio-3-small-sfx) в своём аккаунте Hugging Face.
2. Создать read token в [настройках Hugging Face](https://huggingface.co/settings/tokens), добавить `HF_TOKEN=...` в локальный `.env`. Не добавлять токен в Git.
3. Запустить `docker compose up -d --build`. Уже работающий STT остаётся отдельным сервисом; его профиль `voice` сохраняется.
4. Проверить подготовку: `docker compose logs --tail 30 sfx`. Сообщение `SFX model ready` означает, что веса готовы.
5. В настройках кампании включить звук и генерацию эффектов, создать пробный звук с английским описанием.

Веса и кодировщик сохраняются в томе `sfx-models`, результаты — в `audio/generated`, подписи/параметры/версии/задания — в основной БД. После первой подготовки повторный старт и генерация работают с локальными весами. Не удалять том `sfx-models`, если повторное скачивание нежелательно. Подготовка фиксирует SHA модели в `manifest.json`; `main` не обновляет уже подготовленные веса при каждом старте.

## Библиотека и игра

Настройки кампании → «Сохранённые звуковые эффекты»: создать, прослушать текущую/предыдущие версии, переименовать, закрепить, перегенерировать либо удалить. Управлять может владелец; прослушивать — участники кампании. Перегенерация создаёт новую версию с другим seed. Ошибка не заменяет предыдущий результат. Удаление удаляет все версии; активную задачу сначала нужно дождаться.

Мастер получает инструмент `request_sfx` и список сохранённых `sound_id`. Одинаковое нормализованное описание/контекст/длительность при тех же параметрах модели использует кэш; название не меняет ключ. Для похожего эффекта мастер может выбрать сохранённый ID. Семантического сравнения произвольных описаний здесь нет.

Для каждого выполненного действия без подходящего готового эффекта можно поставить отдельную генерацию; обычный ход обычно даёт 1–2 заявки. Задача фиксируется с игровым действием и не переживает rollback. Результат проигрывается после публикации повествования, только исходной группе и в подходящей сцене. Запоздалый или повторный результат пропускается, но остаётся в библиотеке. Переподключение не проигрывает старые эффекты. Отключение генерации сохраняет возможность пользоваться готовой библиотекой. Громкость и разрешение воспроизведения использует существующий микшер.

## Ограничения и диагностика

По умолчанию CPU, два потока, одно одновременное вычисление на весь сервер, 16 задач в очереди и до четырёх на кампанию. Игровые заявки сначала сохраняются в `staged`, затем допускаются в очередь в короткой транзакции: глобальная блокировка не удерживается на время LLM-хода. Лимит результата — 1–4 секунды; вычисления — 120 секунд, до двух попыток. Каждый inference выполняется в отдельном процессе и освобождает память после завершения. Compose ограничивает сервис двумя CPU и 6 GiB RAM; GPU сервиса STT не резервируется для SFX.

`SFX_TIMEOUT_SECONDS`, `SFX_THREADS`, `SFX_MAX_QUEUE`, `SFX_CAMPAIGN_QUEUE`, `SFX_CACHE_MAX_BYTES`, `SFX_PLAYBACK_TTL` настраиваются в `.env`. Ограничения контейнера: `SFX_CPUS`, `SFX_MEMORY_LIMIT`. `SFX_ENABLED=0` отключает генерацию на сервере. В админке → аудио отображаются готовность модели, очередь, ошибки и объём кэша. Квота по умолчанию 512 MiB, без автоматического удаления пользовательских версий; при её исчерпании удалить ненужные звуки.

CPU может не укладываться в срок актуальности игрового эффекта (15 секунд после публикации). Для заранее подготовленных сохранённых звуков эта задержка отсутствует. Изменение версии весов делает старые задания несовместимыми; перед обновлением опустошить очередь. Старые аудиофайлы продолжают воспроизводиться. Новая перегенерация использует текущую модель с исходным описанием; параметры каждой версии сохраняются отдельно.

Проверка доступа без вывода токена:

```powershell
.venv\Scripts\python.exe -m app.sfx.access
```

Аппаратный пилот после загрузки весов (лучше вне активной игры; использует тот же CPU-бюджет, но не очередь):

```powershell
docker compose exec -T sfx python -m app.sfx.benchmark --output /srv/audio/sfx-pilot --count 3 --duration 3
```

OGG-примеры и `report.json` сохраняются в `audio/sfx-pilot`; отчёт содержит длительность, p50/p95 и максимум RAM дочернего процесса на Linux. Три измерения дают только ориентир. Для решения о live-генерации повторить с `--count 20`, одновременно проверяя задержки LLM и TTS/STT на своей машине. Пилот не публикует игровые события и не создаёт записи в библиотеке; для проверки библиотеки использовать настройки кампании.

Пилот на машине владельца 2026-10-11: три разных эффекта по 3 секунды, CPU/2 потока, 8 шагов, все успешно созданы; p50 23,83 с, p95 24,08 с, пик RAM дочернего процесса 4994 MiB. Время включает загрузку модели в отдельном процессе и кодирование OGG. Это проверка SFX; влияние на одновременные реальные LLM/TTS-запросы отдельно не измерялось. На этой конфигурации полезно заранее готовить библиотеку: типовая генерация дольше окна доставки 15 секунд, результат при этом сохраняется для следующих ходов.

## Разработка без Docker

Создать отдельное окружение Python 3.12 с CPU torch/torchaudio 2.7.1, зависимостями `docker/sfx/requirements.txt`, проектом и установленным `ffmpeg`. Указать `SFX_ENABLED=1`, `SFX_MODEL_DIR=models/sfx`, `SFX_PYTHON=<python отдельного окружения>`. Запустить в этом окружении `python -m app.sfx.prepare`; приложение запускает только координатор, а модель — через `SFX_PYTHON`. Для отдельного координатора `SFX_WORKER_EMBEDDED=0` и `python -m app.sfx` с той же БД/каталогами.

Адаптер `SfxBackend` отделён от очереди, кэша и доставки. Новая модель требует адаптера и отдельной версии параметров/пайплайна; тяжёлые ML-зависимости не добавляются в игровой сервер.
