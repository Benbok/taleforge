# Taleforge — World Objects: этап 0. Схема хранения и контракты

**Статус:** проектное решение, без изменений runtime и БД.  
**База анализа:** `main`, коммит `7f8baf9ffa39c1ffa038a662b945848455859b2d` (2026-10-10).  
**Область:** общая идентичность объектов, контейнеры, гибридная материализация, сюжетные ограничения, карта, идемпотентность.  
**Связанный документ:** [план проверок и внедрения](world-objects-stage0-verification.md).

> Это спецификация *предлагаемых* контрактов и миграций, а не утверждение, что новые поля/таблицы уже присутствуют. Никаких новых функций и миграций этот этап не вводит.

## 1. Цель и зафиксированные решения

Единая система игровых объектов расширяет существующий реестр `Entity`, не создавая конкурирующий реестр «вещей». Техническая модель может описывать, комбинировать и размещать разрешённые объекты, но не определяет игровые числа, награды, сюжетные факты или исходы действий. Первоначальная генерация локации и отложенная генерация содержимого контейнера однократны и сохраняются.

| ID | Решение | Причина |
| --- | --- | --- |
| ADR-01 | `Entity` остаётся источником идентичности предметов и интерактивных объектов в мире | Уже связан с картой, инструментами и событиями |
| ADR-02 | `InventoryItem` сохраняется как механическое представление инвентаря | Не ломать `derive`, `use_item`, экипировку и существующие кампании |
| ADR-03 | Уникальный предмет в инвентаре сохраняет `Entity.id`; `InventoryItem` получает необязательную ссылку на него | Инвентарная строка может меняться, история вещи — нет |
| ADR-04 | Для обычных стаков сохраняется нынешняя схема «сцена ↔ инвентарь» без обязательного постоянного `Entity` | Минимальный объём миграции и записей |
| ADR-05 | Состояние подготовки хранится отдельно от `visited_by` и `Scene` | Разделение генерации, посещения и боевого режима |
| ADR-06 | Материализация имеет уникальный ключ (кампания, цель, фаза) | Нет дублей при параллельном входе |
| ADR-07 | `sketch` — геометрия, `Entity` — взаимодействуемая вещь; между ними нужна устойчивая ссылка | Нет двух шкафов на одной карте |
| ADR-08 | Авторские объекты и ручные правки неприкосновенны для автогенератора | Сохранение действий ведущего |
| ADR-09 | Сюжетные привязки резервируются до случайной добычи | Защита обязательных зацепок |
| ADR-10 | Первой генерации не поручается создавать боевые встречи | Сложность и спавн врагов — действующая боевая архитектура |
| ADR-11 | Генерация и обычное взаимодействие фиксируются через транзакции и `Event` | Согласованность, обратные дельты, диагностика |
| ADR-12 | Старые кампании по умолчанию сохраняют всё содержимое без автоматической перегенерации | Безопасная обратная совместимость |

## 2. Точки интеграции: проверено в коде

- `app/db/models.py`: `Entity(kind, template_id, state, location_id, zone)`, `InventoryItem(character_id, item_template_id, display_name, qty, equipped)`, `Knowledge`, `Scene`, `Event`.
- `app/tools/master/items.py`: `place_item`, `pick_up_item`, `drop_item`, `pass_item`, `keep_found_item`; `_put_in_scene` сейчас объединяет предметы по шаблону/имени/положению; `pick_up_item` удаляет `Entity` при полном подборе.
- `app/core/world.py`: `in_scene_entities` выбирает сущности по `location_id`; `is_scene_item` опирается на флаг `state.item`.
- `app/core/map.py`: `party_map` использует `around`, `scene_view` и `sketch`; `hidden/secret` сейчас обрабатываются преимущественно глобально.
- `app/core/sketch.py`: `features` не имеют постоянного id объекта, геометрия хранится в `Entity.state.sketch`; `for_viewer` фильтрует тайное.
- `app/tools/master/places.py`: `create_location`, `move_heroes`, `enter_room`, `describe_place`, `sketch_place`, `edit_sketch`.
- `app/agents/surveyor.py`: отдельный технический вызов строит эскиз; уже проверяются `layout_rev` и признак ручного изменения.
- `app/core/adventure.py`: комнаты книги создаются лениво, соседние комнаты могут быть созданы до посещения; `scenery` отделено от `encounters`, `treasure` и `secrets`.
- `app/core/plot.py`: `reveals[].clues` хранит `at` и `text`, стабильного `clue_id` пока нет; минимум 3 зацепки в 2 источниках.
- `app/content/catalog.py`: `canon` доступен обычно, `proposal` — при разрешённом тестовом режиме.
- `app/content/schema/core.yaml`: типы `item_template`, `loot_table`, `location_template` существуют, но сами по себе **не гарантируют** наличия исполнителя всех строк таблиц.
- `app/tools/registry.py`: регистрация инструментов, `begin_nested()` для отката, `Event.idempotency_key`.
- `app/gateway/protocol.py`: `map.changed` / `map.state`, генерация OpenAPI и клиентских типов через `app/contract.py`.

**Ограничение совместимости:** геометрия `sketch.features`, `Entity` и `InventoryItem` сегодня независимы. Нельзя начать генерацию «интерактивных шкафов», не определив их синхронизацию.

## 4. Выбранная модель постоянного хранения

### 4.1. `Entity` — первичный экземпляр объекта

Для новых интерактивных сущностей `Entity.kind = "object"`. Поля `id`, `campaign_id`, `name`, `template_id`, `description`, `location_id` и `zone` сохраняют нынешний смысл.

Новые атрибуты располагаются в изолированном `Entity.state.world_object` (версия схемы 1); остальные ключи `state` не перезаписываются:

| Ключ `world_object` | Смысл | Правило |
| --- | --- | --- |
| `schema_version` | Версия контракта | Первоначально 1 |
| `role` | `prop` / `container` / `item` | Отличает интерьер от носимой вещи |
| `capabilities` | Проверенный список действий | Серверный allowlist |
| `unique` | Индивидуальная идентичность | При `true` нельзя складывать с аналогами |
| `origin` | Автор / сюжет / мастер / генератор / действие героя | Не меняется при передаче |
| `generation_ref` | Ссылка на выполнение генерации | Может быть `null` |
| `container_id` | Вложенность внутри мира | `null`, если не вложен |
| `physical` | Состояние объекта | Проверяемая, версионированная структура |
| `access` | Замок/открытие/ловушка, если применимо | Не одно общее `state` |
| `contents` | Статус и ограничения контейнера | Только при возможности `container` |
| `plot_anchor_refs` | Стабильные ссылки на зацепки | Нельзя менять без проверки |
| `visual` | Привязка к эскизу, маркеру или клетке | Не второй источник игровой логики |
| `revision` | Версия состояния объекта | Для optimistic concurrency |

Структура `world_object` хранит *метаданные состояния*, не копию численных механик `item_template`. Урон, броня, эффекты и цены определяются каталогом или разрешёнными игровыми модификаторами.

**Физическое состояние:** `intact` / `damaged` / `destroyed`. Открытость, запертость и срабатывание ловушки — самостоятельные оси, не подменяющие физическое состояние.

**Размещение:** для интерактивного объекта на сцене `Entity.location_id` — эффективная локация; `world_object.container_id` — необязательный родитель-контейнер. Если `container_id` заполнен, объект *не* считается лежащим на полу, даже если `location_id` равен текущей комнате. Все выборки сцены должны исключать вложенные объекты из публичного списка `around`.

Для переносимого уникального объекта в инвентаре `location_id = null` и `container_id = null`; принадлежность задаётся единственной инвентарной строкой, ссылающейся на `Entity`. Это исключает два конкурирующих полных описания размещения. При изменении положения внешнего контейнера эффективная локация вложенных объектов обновляется атомарно либо надёжно выводится из дерева; смешивать эти подходы нельзя. **Для первой реализации зафиксировать атомарное обновление `location_id` для всей вложенной цепочки.**

Для уничтоженного объекта: `physical = destroyed`, `location_id = null`, нет актуальной инвентарной связи. Сам `Entity` уникального объекта сохраняется как «надгробие» для защиты от повторного создания. Уничтожение не означает автоматического стирания истории.

### 4.2. `InventoryItem` — совместимый инвентарь

**Предлагаемая миграция:** добавить необязательное `world_entity_id` (FK на `entities.id`, UNIQUE среди ненулевых). Старые строки остаются без связи. Новые уникальные экземпляры должны иметь эту связь.

Проверки транзакционно:

- `InventoryItem.item_template_id` соответствует `Entity.template_id` или разрешённому варианту найденной вещи.
- Ссылка указывает на `Entity.kind="object"` и на ту же кампанию, что и герой.
- У `Entity` нет активного `location_id`/`container_id`.
- При полном подборе `Entity` **не удаляется** для уникального предмета.
- Для обычных стаков сохраняются `qty` и нынешняя логика, без принудительной записи `Entity` на каждую стрелу.

**Обязательная смена текущего поведения в будущей реализации:** `_put_in_scene` не объединяет уникальные вещи по одному шаблону; `pick_up_item` не удаляет уникальный `Entity`.

### 4.3. `WorldGenerationState` — новая таблица состояния материализации

Предлагаемая таблица `world_generation_states`, одна строка на целевой объект и фазу:

| Поле | Смысл |
| --- | --- |
| `id` | Идентификатор записи |
| `campaign_id` | Кампания |
| `target_entity_id` | Локация либо контейнер (`Entity`) |
| `phase` | `location_initial` / `container_contents` |
| `status` | `unprepared` / `preparing` / `ready` / `blocked` |
| `quality` | `normal` / `fallback` / `legacy_preserved` |
| `revision` | Версия состояния записи |
| `lease_token`, `lease_until` | Право одного исполнителя завершить подготовку |
| `attempt_count`, `last_error` | Управление сбоями |
| `generator_version`, `profile_ref` | Идентификация правил |
| `source_versions` | Снимок цепочки контента и версии сюжета |
| `context_digest`, `reservation` | Хеш контекста и механические резервы |
| `seed` | Закреплённая случайность |
| `result_digest` | Контроль принятого результата |
| `created_at`, `updated_at`, `completed_at` | Аудит |

**Ограничения БД:** UNIQUE (`campaign_id`, `target_entity_id`, `phase`). Проверить целостность кампании и типа цели. Запрещать вторую успешную фиксацию `ready` без *отдельного* явного события изменения мира.

`WorldGenerationState` отвечает за **результат генерации**, а не за физическое состояние содержимого: найденная вещь после переноса не исчезает из истории генерации, но изменяет своё текущее размещение.

Если в конечном состоянии нет предметов, запись остаётся `ready` с пустым результатом. Ошибка не допускает фиксации части созданных объектов.

### 4.4. `PlotAnchorBinding` — привязка сюжетных гарантий

Предлагаемый отдельный индекс `world_plot_bindings`:

- `campaign_id`.
- `anchor_id` — стабильный id источника зацепки (не индекс массива).
- `plot_ref` — тайна / узел / авторское условие.
- `holder_entity_id` — конкретный объект, если уже существует.
- `target_location_id` или ссылка на ожидаемого NPC.
- `state` — `reserved` / `materialized` / `revealed` / `lost` / `replaced_by_story`.
- `source_snapshot` — зафиксированная формулировка обязательства.
- `replacement_ref` — явная ссылка на допустимую альтернативу, если она создана событием.

В текущем `plot.reveals[].clues[]` **нет стабильных id**: `at` и `text` недостаточны для долговечной привязки после `merge_revision`. Требование миграции: новые зацепки должны получать стабильный `clue_id`. Старые получают его один раз при адаптации каркаса; нельзя использовать индекс массива как вечный ключ.

Обязательство «минимум три зацепки минимум в двух источниках» сохраняется; уничтожение физического носителя переводит зацепку в `lost`, не создает магически дубликат.

### 4.5. `Knowledge`, `KnownFact` и видимость

Сохраняем действующие модели личных знаний:

- `Knowledge(character_id, entity_id, level)`.
- `KnownFact` для известных герою фактов.
- `Entity.state` для глобального физического раскрытия и открытия объектов.

Статусы «открыт физически», «виден персонажу», «персонаж знает свойства» не являются одним числом. Для первой версии `Knowledge` можно использовать для допуска персонажа к ранее скрытому объекту; физическое состояние контейнера хранится отдельно. Если впоследствии потребуется независимая история нескольких наблюдений одного предмета, её нужно добавить отдельно, а не переопределять уровни `Knowledge` 0–3.

### 4.6. `sketch.features` и `Entity`

Для интерактивных `features` в будущем предусмотреть необязательное поле `entity_id`, указывающее на `Entity.kind="object"`. Оно связывает *визуальное положение* и *игровую сущность*. При отсутствии ссылки `feature` остаётся декоративным. Новые связанные `features` должны иметь стабильную собственную идентичность для редактирования; поиск только по `name` ненадёжен.

- Положение, проходимость и геометрия остаются компетенцией `sketch`.
- Доступность, содержимое и физический статус — компетенция `Entity`.
- Один связанный объект отображается одним маркером, не ещё одним `scene_view` токеном.
- Данные `sketch.exits` и `state.links` существуют по отдельному текущему контракту: нельзя автоматически превратить каждый выход в новый контейнер/`Entity`. Согласование дверей — самостоятельная задача.
- Изменение `layout_rev` или ручная правка блокирует наложение устаревшего размещения из ответа модели.

## 5. Логические контракты операций (названия не являются существующим API)

### `prepare_location(campaign_id, location_id, trigger, expected_revision)`

**Предусловия:** `Entity.kind="location"`; целевая кампания совпадает; генерация разрешена настройками; отсутствует другой активный владелец подготовки.  
**Вход:** авторские объекты, геометрия, контент, сюжет, уже произошедшие события, состояние встреч.  
**Выход:** `ready` / `blocked` + id подготовки; изменения применены атомарно.  
**Побочные эффекты:** создание только допустимых объектов, фиксация резерва, события после успешного коммита.  
**Идемпотентность:** ключ (`campaign_id`, `location_id`, `location_initial`).

Создание соседней комнаты через `enter_room` не равно `prepare_location`: подготовка запускается в момент фактического доступа или явного предварительного действия ведущего.

### `resolve_container(campaign_id, container_id, actor_id, cause)`

**Предусловия:** цель имеет `container`, доступна в соответствии с физическими правилами; личное раскрытие проверяется отдельно.  
**Выход:** окончательный набор вещей, в том числе пустой.  
**Ограничение:** `resolved` повторно не бросается; до разрушения/высыпания неразрешённого контейнера содержимое материализуется в рамках той же атомарной операции.  
**Идемпотентность:** (`campaign_id`, `container_id`, `container_contents`).

### `interact(actor_id, entity_id, verb, arguments, call_key)`

**Предусловия:** действующий герой, видимость, доступность, расстояние, разрешённая способность, физическое состояние.  
**Действия первой итерации:** `inspect`, `search`, `open`, `close`, `unlock` через существующую механику проверок, `take`, `put`; урон и ловушки — только там, где уже имеется исполняемая механика.  
**Выход:** проверенный результат, события, новая версия объекта и разрешённая проекция.  
**Правило:** клики карты и текстовые намерения приходят к одной серверной операции.

### `transfer_item(actor_id, source, destination, entity_or_inventory_id, qty, call_key)`

Использует существующие инструменты как адаптеры. Для уникального экземпляра обновляет `Entity` и `InventoryItem` в одной транзакции. Для обычного стака применяется текущая логика количества. Запрещён перенос из невидимого контейнера и перенос в другой мир/кампанию.

### `scene_projection(viewer, location_id)`

Только чтение. Формирует `around`, `scene_view`, `sketch`, `book`, содержимое открытых контейнеров и доступные действия с учётом конкретного зрителя. Не запускает LLM, броски и запись новых объектов.

## 6. Гибридный генератор: обязательный протокол

1. Проверить цель и получить разрешение на подготовку (lease с токеном, ограниченным сроком).
2. Создать **снимок входных данных**: ревизия локации и эскиза, реальные объекты, сюжетный каркас, цепочка контента, текущие события; существующие предметы никогда не отбрасывать.
3. Зарезервировать обязательные сюжетные объекты и уникальные находки.
4. Механическим движком отобрать допустимые источники добычи и применить их ограничения.
5. Дать технической модели **ограниченный список разрешённых шаблонов/слотов**, пустые пространства, тему, историю и лимиты; предоставить право формулировать немеханические описания.
6. Получить структурированное **предложение**, не команды записи в БД.
7. Проверить ссылки и `canon/proposal`, количественные ограничения, сюжет, геометрию, уникальность, права изменения, отсутствие монстров из `encounters`.
8. Перед фиксацией убедиться в совпадении lease-токена и версий исходного состояния. Если исходные данные изменились — отвергнуть/перестроить результат.
9. В одной транзакции записать объекты, резервы, статус `ready`, `Event` и изменения проекции.
10. Только после коммита уведомить клиентов (через уже применяемые механизмы `map.changed` / `map.state`).

**Никакого сетевого ответа с частично записанными объектами.**

### Контракт предложения от модели

Допускаются: назначение объекта (`role`), описание, существующий `template_id` из выданного allowlist, предлагаемый слот/клетка, связи между предлагаемыми объектами, несюжетные детали истории.

Запрещены: произвольный `item_template_id` вне allowlist, численные эффекты, скрытое изменение сюжета, новый `creature_template`/`spawn_entity`, изменение `roll_check` и уровней сложности встречи, переписывание существующих `Entity.id`. Сервер назначает реальные id, окончательные количества и механику.

**Отложенность:** механически значимые возможности контейнера фиксируются при его создании (резерв, версия таблицы и seed). При первом `resolve_container` можно просить ИИ только выразить уже допустимое содержимое. Повторный визит не пересчитывает содержимое от уровня героев.

**Стоимость:** повторное чтение `ready` не вызывает модель; `LlmCall.purpose` получает отдельное назначение для генерации, не подменяет действующий `sketch`. Не создавать новый генератор геометрии параллельно `surveyor`.

## 7. Правила источников истины

| Уровень | Авторитетные данные | Как использовать |
| --- | --- | --- |
| Фактические события | `Entity`, `InventoryItem`, `Scene`, `Event` | Исходы, текущая доступность |
| Ведущий | Явные операции через инструменты | Изменения сохраняются как события |
| Сюжет | `CampaignSecret.plot`, `CampaignPlan`, `PlotAnchorBinding` | Гарантии и допустимые изменения |
| Контент | `CatalogView` и авторское приключение | Шаблоны, встречи, сложности, запреты |
| Генератор | Только валидированное предложение | Необходимые новые необязательные объекты |
| Повествование | Проекция сцены | Не порождает состояние без действия |

**Ключевая защита карт книги:** `adventure.room_text` содержит `encounters` и `treasure` как авторские *возможности*. Ни их наличие, ни картинка исходной книги не означают фактического появления токенов. Динамический слой врагов и предметов берётся из сохранённых `Entity`; условия сложности сохраняются за существующим движком боя. Если враг нарисован на растровом фоне, фильтрация токенов не удалит его из изображения — нужна чистая картинка/отдельный слой/редактирование ресурса, без ложного обещания программно стереть пиксели.

## 8. Сценарии согласованности

- **Два героя входят одновременно:** одна строка `WorldGenerationState`, только владелец действующего lease фиксирует результат. Второй читает готовую сцену или получает контролируемое состояние подготовки.
- **Два героя берут одну вещь:** один успешный transfer, второму ошибка `already_taken`; ни двойной выдачи, ни отрицательного остатка.
- **Сундук уничтожен до открытия:** сначала зафиксировать содержимое, затем применить поддерживаемые разрушение/повреждение и правила сохранности; сюжетные последствия фиксируются, а не отменяются.
- **Сундук пуст:** `ready/resolved`, список пуст, генерация больше не вызывается.
- **Появилась записка по сюжету:** отдельное событие создания, не перегенерация `location_initial`.
- **Игрок ушёл, вернулся:** существующие перемещения, сломанные двери, обнаруженные предметы остаются.
- **Архитектор пересмотрел акт:** история материализованных объектов неизменна; новое обязательство проходит проверку конфликта. Если носитель утрачен, статус `lost` и отдельное сюжетное решение, не «телепортация» предмета.
- **Новая модель дала другой текст:** не меняет фактов `ready` и не переписывает увиденное игроками.

## 9. Схема миграции (по будущим PR, без запуска здесь)

1. **Данные без поведения:** добавить `InventoryItem.world_entity_id` (nullable, уникальность), `world_generation_states` и `world_plot_bindings`. Привязки и поля новых объектов строго версионировать. Старые строки `Entity` и `InventoryItem` остаются допустимыми.
2. **Адаптер чтения:** новые объекты читаются через `world_object`, старые `Entity.state.item/landmark` читаются по нынешней семантике. Запретить агрессивный backfill.
3. **Legacy-маркировка:** существующие локации — `ready` + `legacy_preserved`, их содержимое не пересоздавать, даже если `visited_by` пуст. Для ранее созданных комнат-навигаторов допускается *отдельная* явная процедура opt-in подготовки после проверки отсутствия авторских данных. Новые после включения системы — `unprepared`.
4. **Перенос предметов:** новые уникальные экземпляры используют `world_entity_id`; старые стеки не требуют массовой миграции. При необходимости старую конкретную вещь можно явно повысить до уникальной в отдельной операции.
5. **Связь эскиза и Entity:** добавить необязательные стабильные ссылки `feature.entity_id` без массового преобразования старых `features`. Не менять существующий `edit_sketch` до введения правил синхронизации.
6. **Включение по кампании:** новый флаг по умолчанию выключен на существующих кампаниях; после тестирования — включать в новых кампаниях. Отключение генерации не удаляет уже созданный мир.
7. **Откат развертывания:** отключить генератор, сохранив таблицы/метаданные; не удалять созданные `Entity` при выключении флага. Для rollback миграции сначала обеспечить восстановление зависимостей и резервную копию.

**Открытое техническое уточнение на старте реализации:** конкретные типы FK/JSON и ограничения должны быть проверены для используемых SQLite (контракт/тесты) и PostgreSQL (основной runtime). Простая декларация FK не заменяет прикладной проверки `campaign_id` и дерева вложенности.

## 10. Объём Этапа 0 и «не делать»

Этап 0 — только фиксация решений и проверочных контрактов. В этой ветке **нет** новых моделей SQLAlchemy, миграций Alembic, обработчиков инструментов, API-событий или новых UI-кнопок. Первый runtime PR должен реализовать только минимальную модель контейнеров и её тесты, не совмещая это с LLM-генерацией и визуальным редизайном.

Не начинать реализацию генератора до появления тестируемой единой операции переноса уникального объекта, защиты повторной материализации и согласованного отображения `Entity/sketch`.
