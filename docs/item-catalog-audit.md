# Taleforge — аудит библиотеки предметов перед гибридной генерацией

**Дата:** 2026-10-10.  
**Исходная ревизия:** `main` @ `d3ed615ee67279e51517419e29924985beed1a8d`.  
**Статус:** документальный аудит исходных YAML и связанных контрактов приложения; без исправления контента и без изменения runtime.  
**Связанный проект:** World Objects / этап 0, [контракты хранения и генерации](world-objects-stage0.md), если этот документ присутствует в целевой ветке после слияния PR #84.

## 2. Доступность контента — главный блокер

В `app/content/catalog.py` фильтр `CatalogView._ok` допускает `canon`, а `proposal` — только при `allow_proposals=true` (тестовый режим кампании).

В обычном режиме каталог может видеть **85 из 248** описанных шаблонов, если оба пакета подключены. Для сеттинга доступны только **13 из 176** его шаблонов. Это не ошибка валидации, а осознанная политика публикации данных.

**Предписание:** генератор получает именно `CatalogView` конкретной кампании, а не обращается напрямую ко всем YAML. Запрещено глобально переключать все `proposal` в `canon` ради количества добычи. Продвижение записей в канон требует проверки соответствия правилам мира, исполнимости механик и авторского решения.

В `app/content/importer.py` данные пакетов импортируются с версиями и контрольными суммами. Правка уже импортированного YAML **требует повышения версии пакета**, а не изменения данных под прежним номером версии.

## 3. Редкость: что исправлять, а что нет

Выявленные значения `rarity`:

| Значение | Число |
| --- | ---: |
| `common` | 91 |
| `uncommon` | 46 |
| `rare` | 22 |
| `very_rare` | 14 |
| `legendary` | 2 |
| `by_level` | 1 |
| Не указано | 72 |

**Отсутствие редкости в 72 записях не означает 72 ошибки.** Из них **60** — преимущественно стандартное немагическое оружие, доспехи и обычное снаряжение SRD, которым не обязательно присваивать магическую редкость. Ещё **11** — услуги, для которых редкость предмета неуместна. Последняя запись — `item.property_noisy`, описание свойства оружия, а не отдельная добыча.

Запись `item.liquor_formula` использует нестандартную динамическую редкость `by_level`. Генератор не должен сравнивать её напрямую с `rare` / `uncommon` — необходим явный резолвер по версии правила или исключение общего шаблона из случайной раздачи в пользу конкретных `item.formula_*`.

**Рекомендация:** разделить поля `rarity` (магическая/игровая редкость) и `loot_tier` / `spawn_weight` / `availability_tags` (условия генерации). Не навязывать `rarity: common` всем немагическим предметам только ради генератора.

## 4. Таблицы добычи

В `content/echo-leviathans/data/treasure.yaml` находятся **11 записей `loot_table`**, все `proposal`:

- `loot_table.treasure_budget` — бюджет по ярусам, не таблица случайной выдачи (`dice: null`).
- Девять таблиц d20 — три яруса (**1–4**, **5–10**, **11–15**) × три типа источника (**carcass**, **nest**, **syndicate**).
- `loot_table.butchering` — добыча при разделке, `dice: by_source`.

Каждая из девяти d20-таблиц имеет семь строк диапазонов: всего **63 строки**. У `butchering` — девять строк, у таблицы бюджета — три.

В файле обнаружено **58 различных `item.*` ссылок**; все эти id присутствуют среди 248 шаблонов. **56 из 58** ссылаются на записи `proposal` и только две — на `canon`. Это проверка существования *идентификаторов*, а не подтверждение валидности всех строк или исполнимости содержащихся в них механик.

### Типы результатов, которые нельзя сводить к «выдать предмет»

- `item_refs` с `qty` и `choose`.
- `fk` — денежное/товарное значение и формулы бросков.
- `lead_item_ref` — **наводка** на предмет, а не сам предмет.
- `by_scenario: true` — сюжетное разрешение обязательно.
- `npc: true` / `not_loot: true` — персонаж или событие вместо добычи.
- `creature_refs` — контекст события, не случайный переносимый объект.
- `reveal_knowledge`, `story`, `on_cash` и другие специальные эффекты.

**Обязательный шаг до использования:** проверить исполнитель таблиц: что поддерживается движком сейчас, а что является документированным проектом. Нельзя считать строки `loot_table` автоматически действующими правилами, потому что схема их импортирует. Данные `proposal` использовать только в соответствующем режиме.

### Пробел покрываемости

В SRD-пакете нет общего `loot_table`. В сеттинге механические таблицы ограничены тушами, гнёздами, Синдикатами и разделкой.

Для гибридного генератора **пока нет универсального слоя выборки бытового содержимого помещений**: таверн, домов, лабораторий, библиотек, погребов, мастерских, казарм, заброшенных башен, складов. Из существующего `loot_table.tier1_carcass` нельзя автоматически получить правдоподобимое содержимое рабочего стола в доме.

Это не означает необходимости массово добавлять предметы. Нужны **профили локаций и контейнеров, которые выбирают из уже существующего каталога**, дополняя его несистемными вещами.

## 5. Связь с локациями

В просмотренных файлах `location_template`:

| Пакет / источник | Шаблонов | `canon` | `proposal` |
| --- | ---: | ---: | ---: |
| SRD `data/locations.yaml` | 20 | 20 | 0 |
| Эхо `locations/belts.yaml` | 31 | 1 | 30 |
| Эхо `locations/carcasses.yaml` | 28 | 0 | 28 |
| Эхо `locations/routes.yaml` | 7 | 0 | 7 |
| **Итого** | **86** | **21** | **65** |

Среди шаблонов сеттинга есть регионы, маршруты, районы, сюжетные места и туши; не каждый из них является отдельной комнатой для заполнения добычей.

У `item_template` сеттинга широко используются `tags` и `source` (у **165 из 176** записей есть ключ `source`), но явных единообразных полей `location_tags` / `place_tags` для прямого связывания с типами помещений не выявлено.

**Решение:** будущему генератору нужен отдельный явный слой `Generation Profile`, который связывает:

1. Тип помещения и функцию (`laboratory`, `tavern`, `crypt`, `warehouse` и т. д.).
2. Допустимые категории, `source` и теги предметов.
3. Уровень/ярус группы, если применимо.
4. Бюджет, минимальные/максимальные количества.
5. Контейнеры и слоты размещения.
6. Разрешённые таблицы наград и авторские ограничения.

Нельзя вывести такую связь только из `location_type`: `district` или `region` слишком крупны для списка предметов конкретного шкафа.

## 6. Не все `item_template` — переносимая вещь

Проверить семантические исключения до построения общего пула случайного выбора:

- **11 услуг** (`category: service`) — их нельзя положить в сундук.
- `item.property_chitin_alloy` (`weapon_type: variant`, `canon`) и `item.property_noisy` (`weapon_type: property`, `proposal`) — свойства/варианты оружия, а не самостоятельные клинки.
- **11 уникальных реликвий** (`unique: true`), все `proposal` — должны появляться по явному авторскому или сюжетному разрешению, не обычным `spawn_weight`.
- `item.liquor_formula` — общий шаблон с `rarity: by_level`; рядом есть **11 конкретных формул** с обычными уровнями редкости.
- Часть результатов добычи — услуги, информация, деньги, спасаемые NPC или сюжетные зацепки, не экземпляры `Entity(kind="object")`.

У генератора должны быть отдельные семантические признаки `spawnable`, `transferable`, `stackable`, `story_gate`, `supported_mechanics` — явные правила, а не косвенный вывод из названия.

## 7. Проверка исполнимости механики

В контенте обнаружено **шесть шаблонов** с `op: custom`:

- `item.fat_lamp`.
- `item.implant_nerve_shunt`.
- `item.relic_hunger_compass`.
- `item.relic_sounding_port`.
- `item.relic_archive_crystal`.
- `item.relic_protocol_seal`.

Все шесть — `proposal`. В `app/content/loader.py` `op: custom` специально отмечается как неформализованная заявка на механику и не должен считаться действующим эффектом.

**Политика для генератора:** такие предметы могут быть допущены сюжетно/в тестовом режиме, но недопустимо сообщать игрокам об эффекте как гарантированно реализованном, пока соответствующая механика не проверена. Для MVP автоматической выдачи исключать любой шаблон с неподдерживаемыми обязательными эффектами.

`app/tools/master/items.py` использует `spell_scroll` и операции `modifiers` / `use` для предметов. Наличие других полей, описаний и триггеров в YAML само по себе не гарантирует, что они исполнены сервером.

## 8. Приоритеты подготовки данных к World Objects

### P0 — до запуска генератора

1. **Гейт канона.** Определить набор разрешённых `canon` для начальных тестов; не повышать `proposal` массово.
2. **Типизированный пул.** Исключать услуги, свойства оружия, недопустимые `unique` и неподдерживаемые эффекты.
3. **Семантика выпадения.** Вводить явные `spawnable` / `story_gate` и валидировать категории.
4. **Резолвер таблиц.** Разделить реальные предметы, деньги, NPC, подсказки, условные награды и бюджет.
5. **Сохранение результатов.** Один раз материализованный контейнер не генерируется снова.

### P1 — минимальное контекстное наполнение

Создать **пилотные профили** для 6–8 типов помещения: таверна, дом, склад, лаборатория, склеп, пещера, мастерская, казарма. Это профили, *не обязательно новые предметы*. Для них описать:

- 3–6 возможных интерактивных объектов/контейнеров.
- Профиль обычных немеханических предметов.
- Разрешённые теги и источники механических вещей.
- Ограничения и частоту находок.
- Возможность «пустого» результата.

Дополнить **универсальными архетипами контейнеров** (сундук, ящик, шкаф, мешок, тайник, стойка, ящик стола) и обычных объектов, которые модель описывает свободно. Архетип — тип взаимодействия, а не обязательная новая строка `item_template`.

### P2 — расширение сеттинга

После механической проверки и авторского согласования переводить выбранные `proposal` в `canon` **по категориям**, начиная с часто используемых расходников, снаряжения, боеприпасов и торговых товаров. Для каждой категории проверять реальные методы `use_item` / `resolve_attack` / магазинной экономики.

Реликвии и импланты — отдельное позднее направление, поскольку имеют сложную механику и сюжетную значимость.

### P3 — расширение разнообразия

По наблюдениям игровой практики дополнять каталог только там, где реально не хватает *механически отличимых* предметов. Для описаний бытовых вещей и микроисторий не требуется тысячи новых `item_template`.

## 10. Ответ на вопрос «Нужно ли наполнять базу?»

**Нужно поддерживать библиотеку правил и предметных шаблонов, но не заполнять SQL-базу вручную и не создавать огромный каталог декоративных вещей.**

Оптимальная последовательность:

1. Исправить модель выбора допустимого контента.
2. Реализовать профили помещений/контейнеров.
3. Переиспользовать 248 уже описанных шаблонов с соблюдением `canon/proposal`.
4. Добавлять новые шаблоны только под отсутствующие игровые механики.
5. Использовать техническую модель для немеханического разнообразия и контекстных описаний.
6. Хранить реальные экземпляры и историю их перемещений в игровом мире.

**Ключевой вывод:** прежде чем расширять список предметов, требуется сделать имеющийся каталог безопасным и пригодным для управляемой генерации.

### Методика и ограничения аудита

Проверены исходные файлы из конкретного коммита; записи считались по top-level `items[]` с `id`. Метаданные `status`, `category`, `rarity`, `unique` и ссылочные токены проверялись по YAML-тексту; количество строк таблиц оценивалось по структуре вложенных `rows`. Кросс-ссылки проверены на существование `item.*` id **в проверенных файлах**. Это не равно запуску YAML-парсера, `load_with_dependencies`, SQL-импортера, боевого движка или тестов приложения. Не установлена реальная выборка импортированных в пользовательскую БД версий.

Отдельно проверены связанные кодовые контракты: `app/content/catalog.py`, `app/content/loader.py`, `app/content/importer.py`, `app/tools/master/items.py` и схема `app/content/schema/core.yaml`. Вывод о поддержке механик ограничен явными проверенными точками; полноценный runtime-аудит исполнения всех модификаторов находится вне этого документа.
